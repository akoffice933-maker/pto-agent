# 2. Цель, назначение и границы

## 2.1 Цель

Создать систему, которая берёт на себя **60–80 % рутинных операций** инженера ПТО: подготовку, проверку и ведение исполнительной документации, сверку объёмов, формирование КС-2/КС-3, нормативный контроль, подготовку исполнительных схем и отчётности, — при сохранении полного контроля и подписи за человеком.

## 2.2 Задачи

1. Приём запросов на естественном языке (текст, голос) и команд из интерфейса/мессенджера.
2. Чтение и структурирование документов: PDF (в т.ч. сканы), DOCX, XLSX/CSV, DWG/DXF, IFC, выгрузки 1С и сметных программ.
3. Формирование черновиков документов по корпоративным шаблонам с сохранением формата, шрифтов, рамок и штампов.
4. Поиск расхождений между проектом, фактом, сметой и актами субподрядчиков с указанием причины и источника.
5. Нормативная проверка с обязательной ссылкой на конкретный пункт СП/ГОСТ/СНиП, включая версию и дату редакции.
6. Контроль комплектности пакетов ИД по видам работ и объектам.
7. Подготовка исполнительных схем: анализ redline, формирование команд изменения чертежа, выпуск схемы со штампом «Исполнительная схема».
8. Полное протоколирование действий агента и прослеживаемость «документ → источник → решение → подпись».

## 2.3 Входит в объём работ (In scope)

- Все сценарии разделов 4, 5 и 6 настоящего ТЗ.
- Собственная база нормативных документов с версионированием.
- Интеграции, перечисленные в разделе 9 (в объёме MVP — 1С и файловое хранилище/ЭДО).
- Веб-интерфейс АРМ инженера ПТО + интерфейс согласования.
- Развёртывание on-premise или в защищённом облаке (требование обязательно для госсектора и крупных застройщиков).

## 2.4 Не входит в объём (Out of scope)

| Что не делает система | Обоснование |
|---|---|
| Не подписывает документы (ЭП/УКЭП) и не передаёт их заказчику без участия человека | Юридические требования, принцип HITL |
| Не принимает проектных решений и не изменяет проектную документацию | Ответственность ГИП и авторского надзора |
| Не выполняет функции экспертизы проектной документации | Отдельный процесс и лицензируемая деятельность |
| Не ведёт бухгалтерский и налоговый учёт | Зона 1С и бухгалтерии |
| Не заменяет натурные измерения и геодезический контроль | Факт подтверждается только на объекте |
| Не выдаёт заключений о соответствии объекта | Зона органа стройнадзора |

## 2.5 Базовые принципы проектирования

| Принцип | Реализация в системе |
|---|---|
| Human-in-the-loop | Любое действие с внешним эффектом (запись файла, отправка, выпуск схемы, изменение чертежа) требует явного подтверждения; по умолчанию агент работает в режиме «черновик» |
| Доказуемость | Каждое утверждение в сформированном документе снабжено ссылкой на источник (лист, пункт, строка таблицы, GUID элемента BIM) |
| Детерминизм расчётов | Арифметика (объёмы, суммы, НДС, индексы) выполняется кодом, не моделью; LLM отвечает за извлечение и объяснение |
| Воспроизводимость | Любой артефакт можно пересобрать из зафиксированного набора входных данных, версии промпта и версии модели (фиксация seed/version в журнале) |
| Изоляция данных | Данные одного объекта и одной организации недоступны другим; разделение прав на уровне строк (RLS) |
| Приоритет безопасности перед полнотой | При низкой уверенности агент не догадывается, а формирует запрос уточнения или направляет задачу человеку |
| Обратимость | Все изменения чертежей и документов выполняются через diff-подтверждение с возможностью откатa |

# 3. Роли пользователей и права

| Роль | Основные действия | Ограничения |
|---|---|---|
| Инженер ПТО | Запуск сценариев, загрузка документов, правка черновиков, отправка на проверку | Не может менять настройки RAG и нормативную базу |
| Ведущий инженер / нач. участка | Согласование АОСР и схем, подтверждение факта работ | Не может подписывать за заказчика |
| Начальник ПТО | Утверждение пакетов ИД, реестров, шаблонов | Не может отключать логирование |
| Сметчик | Работа со сметами, расценками, индексами, сверка КС-2 | Нет доступа к модулю ИС |
| Технадзор / заказчик (внешний) | Просмотр переданных пакетов, замечания | Только чтение, только по своим объектам |
| Администратор системы | Пользователи, роли, интеграции, база знаний | Не видит содержимое документов объектов без отдельного разрешения |
| Аудитор / ИБ | Просмотр журналов действий и версий | Только чтение журналов, без права изменения |
| ГИП (согласующий) | Согласование изменений, затрагивающих проект | Нет доступа к финансовым данным |

Требование: **RBAC + атрибутный доступ** (объект, договор, раздел проекта), журналирование каждого доступа к документам.

## 4.1 С-01. Формирование акта КС-2 и справки КС-3

**Назначение:** собрать черновик КС-2 за отчётный период на основании журнала работ/КС-6а, сметы и фактических объёмов, со сверкой по расценкам, и сформировать КС-3 по набору актов.

**Триггер:** запрос в интерфейсе, в чате или по расписанию (последний рабочий день месяца).

**Входные данные:**
- смета (XLSX/выгрузка Гранд-Смета/Smeta.ru) — шифр расценки, наименование, единица, объём, цена;
- журнал работ / КС-6а / суточные отчёты;
- договор и допсоглашения (лимиты, коэффициент, НДС, аванс);
- ранее закрытые КС-2 по объекту (для накопительного учёта);
- корпоративный шаблон КС-2 (DOCX/XLSX).

**Ход выполнения:**
1. Агент идентифицирует объект, договор, отчётный период (при неоднозначности — задаёт уточняющий вопрос).
2. Извлекает позиции сметы в структурированный вид (шифр, наименование, ед., объём, цена), отмечая неоднозначные строки.
3. Извлекает фактически выполненные объёмы из журнала/отчётов за период, привязывает к позициям сметы (по шифру, наименованию, единице).
4. Выполняет **кодом**: расчёт стоимости позиций, итогов, НДС, накопительных значений, сверку с лимитами договора и ранее закрытыми объёмами.
5. Формирует таблицу расхождений: объём сверх сметы, единицы не совпадают, позиция отсутствует в смете, дубль позиции, цена отличается от сметной, работа не подтверждена ИД.
6. Формирует черновик КС-2 и КС-3 по шаблону (заполнение полей, сохранение форматирования).
7. Показывает пользователю предпросмотр + список расхождений + список «требует ИД».
8. После подтверждения сохраняет документы в хранилище, формирует версию и запись в журнале.

**Выходные данные:** КС-2 (DOCX и XLSX), КС-3 (DOCX/XLSX), таблица расхождений (XLSX), карточка «позиции без ИД».

**Приёмочные критерии:**

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-01.1 | Черновик КС-2 на 50 позиций формируется не более чем за 10 минут (включая загрузку файлов) | Хронометраж на пилоте, 10 прогонов |
| AC-01.2 | Доля позиций, требующих ручной правки, ≤ 20 % | Сверка с эталонным актом на golden set из 30 актов |
| AC-01.3 | Точность извлечения объёмов из журналов (F1) ≥ 0,95 на машиночитаемых файлах и ≥ 0,85 на сканах | Golden set, ручная разметка |
| AC-01.4 | Ошибки арифметики в выпущенных документах — 0 | Автоматическая перепроверка кодом + контрольная сверка |
| AC-01.5 | Каждая позиция акта имеет ссылку на строку сметы и на документ-основание факта | Проверка атрибутов в карточке позиции |
| AC-01.6 | Расхождения типов «сверх сметы», «нет в смете», «цена ≠ сметной» выявляются в 100 % случаев на golden set с заложенными ошибками | Golden set из 30 актов с 90 заложенными ошибками |
| AC-01.7 | КС-3 консолидирует выбранные КС-2 с совпадением итогов до копейки | Автотест на наборе из 5 актов |
| AC-01.8 | Экспорт не ломает корпоративный шаблон (шрифты, рамки, штамп, колонтитулы) | Визуальная и программная проверка |

**Ограничения:** агент не определяет правомерность применения расценки — только сигнализирует о несоответствии; спорные позиции помечаются и передаются сметчику.

## 4.2 С-02. Сверка объёмов (проект ↔ факт ↔ акты субподрядчиков)

**Назначение:** выявить расхождения между проектными объёмами (ВОР/смета/BIM), фактическими (журналы, замеры, ИД) и объёмами в актах субподрядчиков.

**Входные данные:** ВОР/смета, выгрузка объёмов из BIM (IFC или таблица), журналы работ, акты субподрядчиков, ранее оплаченные акты.

**Ход выполнения:**
1. Нормализация номенклатуры: приведение наименований работ к единому справочнику (синонимы, сокращения, разные единицы измерения — м ↔ м², шт ↔ компл.).
2. Построение трёхсторонней матрицы сопоставления по ключу (шифр расценки + вид работ + зона/этаж/захватка).
3. Расчёт отклонений в абсолютных и относительных величинах, проверка на дубли между актами разных субподрядчиков.
4. Классификация расхождений по критичности: критичное (двойной учёт, объём больше проектного), существенное (отклонение > 5 %), информационное (единицы, округления).
5. Формирование таблицы расхождений с подсветкой и ссылками на листы/строки источников.

**Приёмочные критерии:**

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-02.1 | Автоматическое сопоставление позиций номенклатуры ≥ 90 % (по строкам) | Golden set 500 строк |
| AC-02.2 | Двойной учёт объёмов между субподрядчиками выявляется в 100 % случаев | Golden set с 25 заложенными дублями |
| AC-02.3 | Таблица расхождений содержит для каждой строки: источник, лист/строку, величину отклонения, критичность, предлагаемое действие | Проверка структуры отчёта |
| AC-02.4 | Время подготовки сводной таблицы по объекту на 1000 позиций ≤ 15 минут | Хронометраж |
| AC-02.5 | Ложноположительные срабатывания ≤ 10 % | Ручная проверка выборки 100 строк |

## 4.3 С-03. Контроль комплектности пакета ИД

**Назначение:** проверить, что по каждому виду работ/этапу собран полный комплект ИД в соответствии с требованиями (СП 48.13330, РД-11-02-2006, требования заказчика).

**Ход выполнения:**
1. Определение вида работ по позиции акта/сметы (классификатор видов работ).
2. Построение матрицы «вид работ → требуемые документы» (Приложение A) с учётом требований конкретного заказчика.
3. Проверка фактического наличия, актуальности и корректности заполнения каждого документа: даты в правильной последовательности, ссылки на проектную документацию, наличие подписей/штампов, приложений, сертификатов.
4. Формирование отчёта комплектности: «есть / отсутствует / есть с замечаниями», с указанием, что именно нарушено.
5. Уведомление ответственного за недостающими документами (в интерфейсе/Telegram).

**Приёмочные критерии:**

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-03.1 | Матрица требований комплектности настраивается без разработчика (через админ-интерфейс/справочник) | Демонстрация настройки на новом заказчике за 1 час |
| AC-03.2 | Отсутствующие документы выявляются в 100 % случаев на golden set из 20 пакетов | Golden set с известным составом |
| AC-03.3 | Проверка хронологии дат (АОСР не ранее начала работ, акт не ранее АОСР) реализована и покрыта тестами | Автотесты |
| AC-03.4 | Отчёт комплектности формируется в XLSX и PDF, пригоден для отправки заказчику | Проверка формы отчёта |
| AC-03.5 | Среднее время проверки пакета из 40 документов ≤ 5 минут | Хронометраж |

## 4.4 С-04. Формирование АОСР и журналов работ

**Назначение:** подготовить АОСР на скрытые работы по факту выполнения, с автоматическим подбором нормативных требований, материалов и приложений.

**Ход выполнения:**
1. Определение вида скрытых работ и привязки (ось, захватка, этаж, помещение).
2. Подбор применимых нормативных документов и пунктов (из RAG-базы, с указанием редакции).
3. Подбор применённых материалов из входного контроля (паспорта, сертификаты, декларации) с реквизитами документов о качестве.
4. Заполнение формы АОСР по шаблону, формирование приложений (исполнительные схемы, сертификаты).
5. Проверка на типовые ошибки (отсутствие ссылки на РД, несоответствие дат, отсутствие подписей, не тот объект/шифр).
6. Предпросмотр и передача на согласование.

**Приёмочные критерии:**

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-04.1 | АОСР формируется на основе данных журнала и входного контроля без ручного ввода реквизитов в ≥ 80 % полей | Проверка на 20 реальных АОСР |
| AC-04.2 | Все нормативные ссылки в АОСР актуальны на дату формирования и содержат пункт | Автопроверка по базе + выборочная ручная |
| AC-04.3 | Автоматически выявляются 100 % АОСР с нарушением хронологии дат на golden set | Golden set с 15 нарушениями |
| AC-04.4 | Форма соответствует требованиям РД-11-02-2006 (состав полей) и корпоративному шаблону | Экспертная проверка начальником ПТО |

## 4.5 С-05. Нормативная проверка со ссылками на пункты

**Назначение:** ответить на вопрос «соответствует ли решение/документ норме» с обязательной цитатой и указанием редакции, либо выявить несоответствия в комплекте документов.

**Ход выполнения:**
1. Классификация запроса: справка / проверка документа / проверка решения / поиск требования.
2. Поиск в RAG-базе с фильтрами по типу документа (СП, ГОСТ, СНиП, ФЕР/ТЕР), статусу (действует/отменён), дате введения.
3. Формирование ответа: вывод → цитата пункта → реквизиты документа → дата актуальности → степень уверенности.
4. Если норма отменена или заменена — обязательное указание действующей замены.
5. Если однозначного ответа нет — явный отказ с перечнем найденных близких норм и рекомендацией экспертной проверки.

**Приёмочные критерии:**

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-05.1 | 100 % ответов содержат реквизиты документа, номер пункта и дату редакции | Автопроверка формата ответа |
| AC-05.2 | Точность цитирования (цитата дословно присутствует в указанном пункте) ≥ 99 % | Golden set 200 вопросов |
| AC-05.3 | Доля ответов с «галлюцинированными» ссылками (несуществующий пункт) ≤ 0,5 % | Golden set + выборочный аудит |
| AC-05.4 | Корректность ответа (совпадает с эталоном эксперта) ≥ 90 % | Golden set 200 вопросов, слепая оценка двух экспертов |
| AC-05.5 | Отменённые нормы не предлагаются как действующие — 100 % | Тесты на 30 отменённых документах |
| AC-05.6 | Время ответа ≤ 15 с (p95) | Нагрузочный тест |

## 4.6 С-06. Письма, претензии, служебные записки, ответы на замечания

**Назначение:** подготовка корреспонденции по фактам, выявленным системой (расхождения, недостающая ИД, нарушения сроков, замечания технадзора).

**Требования:**
- шаблоны по типам писем (претензия, уведомление, ответ на предписание, запрос разъяснений, служебная записка);
- автоматическая подстановка фактов со ссылками на документы (акт, пункт договора, дата);
- обязательная проверка: нет ли в письме утверждений без документального подтверждения;
- ссылки на пункты договора/СП при обосновании позиции;
- нумерация и регистрация в журнале исходящей корреспонденции.

**Приёмочные критерии:** AC-06.1 — письмо формируется ≤ 2 минут; AC-06.2 — 100 % фактов в письме имеют ссылку на документ; AC-06.3 — шаблоны редактируются без разработчика; AC-06.4 — экспертная оценка пригодности черновика ≥ 4 из 5 баллов на 20 письмах.

## 4.7 С-07. Реестр ИД и передача пакета

**Требования:** автоматическое формирование реестра (Приложение C) с нумерацией, составом, количеством листов, привязкой к актам КС-2 и позициям сметы; формирование описи и сопроводительного письма; фиксация факта передачи (дата, получатель, статус) и замечаний заказчика с обратной связью в карточки документов.

# 6. Модуль исполнительных схем (дополнение к ТЗ)

## 6.1 Цель и место в системе

Автоматизировать подготовку и актуализацию исполнительных схем в AutoCAD / nanoCAD и аналогах на основе проектных чертежей, полевых изменений (redline, фото, журналы, АОСР) и данных BIM, с выпуском схемы в форматах, пригодных для передачи в составе ИД.

Ключевая ценность: инженер не «перерисовывает», а **проверяет и подтверждает** подготовленные изменения.

## 6.2 Границы модуля

**Входит:** чтение DWG/DXF, анализ redline-разметки, генерация изменений геометрии и атрибутов в пределах согласованных операций, оформление (слои, рамки, штампы, масштабы), выпуск PDF/DWG/DXF, diff-подтверждение, связка с АОСР/КС-2.

**Не входит:** полное проектирование с нуля, расчёт конструкций, выпуск проектной документации, автоматическое принятие решений об изменении проектных решений (только через ГИП и авторский надзор).

## 6.3 Сценарии модуля

### ИС-01. Генерация исполнительной схемы из описания / таблицы изменений / АОСР

**Вход:** исходный проектный DWG/DXF (или BIM-вид), описание изменений текстом, таблица координат/привязок, АОСР с перечнем работ.
**Ход:** определение типа схемы → выбор шаблона оформления → построение/корректировка геометрии по описанию → нанесение размеров, отметок, подписей, номеров элементов → заполнение штампа и приложений → валидация → предпросмотр PDF → подтверждение → выпуск.
**Приёмка:**

| ID | Критерий | Метод |
|---|---|---|
| AC-ИС-01.1 | По описанию изменений из 10 пунктов формируется схема, в которой ≥ 90 % элементов размещены в соответствии с эталонной схемой (проверка по контрольным точкам/размерам) | Сравнение с эталоном на 10 реальных кейсах |
| AC-ИС-01.2 | Оформление соответствует корпоративному шаблону: слои, шрифты (ГОСТ тип А/Б), рамка, штамп, масштаб | Программная проверка слоёв и блоков + визуальная |
| AC-ИС-01.3 | Схема выпускается в PDF с масштабом печати, соответствующим листу, и в DWG, открывающемся без ошибок в AutoCAD и nanoCAD | Открытие в обеих САПР, проверка предупреждений |
| AC-ИС-01.4 | Время подготовки схемы типового узла ≤ 15 минут против 2–4 часов вручную | Хронометраж |
| AC-ИС-01.5 | Каждая схема связана с АОСР и позициями КС-2 (обратные ссылки в карточке) | Проверка карточки документа |

### ИС-02. Обновление существующих DWG по redline-разметке

**Вход:** исходный DWG/DXF, скан/PDF с пометками, фото объекта, текстовые комментарии.
**Ход:** регистрация растра по чертежу (масштаб, поворот, привязка) → распознавание пометок (vision + OCR + геометрия) → классификация пометок (добавить/удалить/перенести/изменить диаметр/отметку) → формирование списка операций → diff-предпросмотр (подсветка: что изменится) → подтверждение по каждой операции или группой → применение → сохранение версии «Исполнительная схема».
**Приёмка:**

| ID | Критерий | Метод |
|---|---|---|
| AC-ИС-02.1 | Точность распознавания типов пометок ≥ 85 % на golden set из 100 redline-пометок | Размеченный набор |
| AC-ИС-02.2 | Пропуск пометки (не распознана и не показана человеку) ≤ 5 % — приоритет полноты над точностью | Golden set |
| AC-ИС-02.3 | Все нераспознанные/неоднозначные пометки выводятся в отдельный список «требует решения инженера» | Проверка интерфейса |
| AC-ИС-02.4 | Ни одно изменение не применяется к файлу без явного подтверждения; сохраняется исходная версия | Проверка журнала и версий |
| AC-ИС-02.5 | Регистрация растра обеспечивает совмещение пометок с чертежом с погрешностью ≤ 2 мм в масштабе листа на 20 тестовых парах | Измерение по контрольным точкам |

### ИС-03. Проверка комплектности и соответствия схем фактическому состоянию

- Проверка набора схем по видам работ и захваткам (нет ли пропущенных).
- Проверка, что схема соответствует АОСР по датам, составу работ и объекту.
- Проверка внутренней согласованности: отметки, диаметры и длины в схеме совпадают с объёмами в КС-2, а марки материалов — с входным контролем.
- Проверка «схема не старше проекта»: используется ли актуальная редакция РД (по штампу/версии CDE).

Приёмка: 100 % выявление схем, ссылающихся на отменённую редакцию РД, на golden set из 15 случаев; отчёт о рассогласованиях «схема ↔ КС-2» формируется автоматически.

### ИС-04. Экспорт в стандартные форматы ПТО

- Выпуск PDF (для ИД), DWG (для заказчика/эксплуатации), DXF (для обмена), при необходимости — растровых копий.
- Автоматическая подстановка штампа «Исполнительная схема» с реквизитами: объект, шифр, вид работ, исполнитель, дата, подписи, ссылка на АОСР.
- Формирование пакетного выпуска (комплект схем раздела) с перечнем и нумерацией листов.

### ИС-05. Связка схемы с КС-2 и журналом работ

- Из схемы извлекается ведомость объёмов (длины, площади, количество элементов) и сопоставляется с позициями КС-2.
- Расхождение более порога (по умолчанию 5 %) помечается как замечание.
- Обратная навигация: из позиции акта открывается фрагмент схемы с подсветкой соответствующего участка.

- Все числовые значения на схеме (длины, отметки, диаметры) должны быть либо извлечены из источника с указанием источника, либо вычислены кодом; запрещено «додумывать» числа моделью.
- Единицы измерения и масштаб проверяются явно: агент обязан определить масштаб чертежа и подтвердить его у пользователя при первом использовании файла.
- При конфликте redline и АОСР приоритет — у АОСР/акта, помеченного как подписанный; конфликт выводится на человека.

## 6.6 Архитектура CAD-модуля

```
Инженер ПТО
   │ (redline PDF / фото / описание / АОСР)
   ▼
CAD-агент («Чертёжник»)
   ├── Препроцессор: регистрация растра, OCR, vision-анализ пометок
   ├── Планировщик операций → список типизированных операций (JSON)
   ├── Валидатор операций (правила + шаблон + белый список)
   ├── Исполнитель:
   │     ├── Live-мост  → AutoCAD/nanoCAD через COM или MCP-плагин
   │     ├── Headless   → ezdxf (+ ODA File Converter для DWG)
   │     └── LISP-генератор → .lsp для пакетного применения
   ├── Diff/Preview → PDF + растр с подсветкой
   ├── Оформление → слои, рамка, штамп, масштаб, выпуск
   └── Журнал + версия + связка с АОСР/КС-2
   ▼
HITL-подтверждение (пооперационно или группой)
   ▼
Выпуск: PDF + DWG/DXF + запись в реестр ИД
```

## 6.7 Варианты реализации и обоснование выбора

| Вариант | Плюсы | Минусы | Когда выбирать |
|---|---|---|---|
| Headless на ezdxf (DXF) | Работает на сервере, без лицензий САПР, стабильно, дёшево, легко тестировать | Не работает с DWG напрямую (нужен ODA-конвертер), не поддерживает сложные объекты (AEC-объекты, динамические блоки частично) | Базовый вариант для генерации схем из описаний и простых изменений — **рекомендуется для MVP** |
| ODA File Converter + ezdxf | DWG ↔ DXF на сервере, покрывает большинство случаев | Требует лицензии ODA, конвертация может терять специфичные объекты | Когда заказчик работает в DWG и нельзя ставить САПР на сервер |
| Live-мост (COM/плагин, MCP) | Максимальная совместимость, видны все объекты, можно использовать штатные команды и шаблоны | Требует установленного AutoCAD/nanoCAD и лицензии, не масштабируется горизонтально, нестабильно при падениях САПР | Работа «в живом чертеже», сложные изменения, случаи с динамическими блоками |
| Генерация AutoLISP | Не требует прямого API, применяется человеком вручную или пакетно, легко проверяется | Ограниченная обратимость, риск ошибочных команд, нужен контроль версии САПР | Как резервный путь и для типовых операций |

**Решение для MVP:** headless-first (ezdxf + ODA при необходимости), live-мост — как опция «премиум» для сложных объектов; все операции описываются в едином типизированном виде, поэтому смена исполнителя не меняет логику агента.

## 7.4 Пайплайн обработки документа (типовой)

1. Приём файла → антивирус → определение типа → разметка страниц.
2. Извлечение: текстовый слой; при отсутствии — OCR; таблицы — структурированное извлечение.
3. Классификация документа (тип, объект, вид работ, период) с порогом уверенности.
4. Нормализация в целевую схему (JSON по типу документа) + запись источников на уровне полей (page/bbox/строка).
5. Валидация схемой (Pydantic) + бизнес-правила + перекрёстные проверки.
6. Сохранение в БД с версией, попадание в очередь задач для агентов.
7. Отчёт «что извлечено, где не уверены» → человеку.

# 8. Требования к нормативной базе и RAG

| ID | Требование |
|---|---|
| FR-RAG-01 | База включает СП, ГОСТ, СНиП, СанПиН (в части), технические регламенты, ФЕР/ТЕР/ГЭСН, а также локальные нормативы заказчика |
| FR-RAG-02 | **Версионирование обязательно:** для каждого документа хранятся редакции с датами введения/отмены, статусом (действует/отменён/заменён) и ссылкой на заменяющий документ |
| FR-RAG-03 | Каждый чанк содержит: обозначение документа, номер пункта, полный текст пункта (не обрезанный), редакцию, дату актуальности |
| FR-RAG-04 | Ответ всегда формируется в формате: вывод → цитата → реквизиты → дата актуальности → уверенность |
| FR-RAG-05 | Фильтрация поиска по дате: при проверке документа, подписанного в 2021 году, применяются нормы, действовавшие на ту дату (с указанием этого факта) |
| FR-RAG-06 | Запрет на цитирование фрагмента, отсутствующего в источнике: цитатный валидатор сверяет ответ с извлечёнными чанками и блокирует выдачу при несовпадении |
| FR-RAG-07 | Гибридный поиск (BM25 + вектор) + реранкер (bge-reranker) — обязательно для нормативки |
| FR-RAG-08 | Обновление базы: регламентная процедура с контролем изменений (что добавлено/изменено/отменено), уведомление пользователей о затронутых документах |
| FR-RAG-09 | Поддержка «нормативных наборов» по объекту/заказчику (какие документы применимы) |
| FR-RAG-10 | Golden set для оценки качества RAG (≥ 200 вопросов с эталонными ответами и ссылками), регрессионное тестирование при каждом обновлении базы или модели |
| FR-RAG-11 | Возможность указать приоритет: СП и ГОСТ выше СНиП; отменённый СНиП не предлагается как действующий |
| FR-RAG-12 | Прозрачность: пользователь может открыть исходный документ на указанном пункте (переход к странице) |

**Метрики качества RAG:** Recall@5 ≥ 0,9; точность цитаты ≥ 99 %; доля ответов без ссылки — 0; доля «нет ответа» на вопросы вне базы — корректный отказ ≥ 95 %.

Разметка выполняется экспертами ПТО, хранится в закрытом контуре, версионируется вместе с промптами. Любое изменение модели/промпта проходит регрессию на golden set.

# 14. Аудит open-source решений (проверено через GitHub API 02.11.2026)

## 14.1 Важное предупреждение по лицензиям

При проверке выявлены критичные для проекта обстоятельства:

- **Отсутствие лицензии ≠ свободное использование.** По умолчанию отсутствие файла лицензии означает «все права защищены»: код нельзя включать в поставку без письменного разрешения автора. Это относится к `ivanpetrov19960407-afk/construction-ai-core`, `14Segun88/moge-document-expertise-ai`, `Rohianon/construction-submittal-agent`, `Sumitkumar005/Construction-AI-Agent`, `LordQueso/MCP-construction`, а также к `constructelligence-lab/construction-prompts`, `wyuebei-cloud/detail-to-lsp`, `A-SHOJAEI/ConstructDrawingAI` (файл лицензии есть, но не распознан автоматически — требуется юридическая проверка вручную).
- **`dvdobrovolskiy/AutoGAD` распространяется под AGPL-3.0.** AGPL требует раскрытия исходного кода производной системы при предоставлении доступа по сети — неприемлемо для коммерческого/закрытого продукта. Допустимо: изучение архитектуры, использование как отдельного самостоятельного сервиса при согласии юристов, либо коммерческая лицензия от автора (запросить).
- **Вывод:** «готового каркаса под российские документы» для прямого переиспользования нет. Реалистичная стратегия — собственная сборка, где open-source используется как набор приёмов, промптов и **разрешаемых по лицензии** библиотек.

| Вариант | Плюсы | Минусы | Когда разумно |

# 16. Порядок приёмки и критерии go/no-go для пилота

## 16.1 Критерии приёмки MVP

1. Все сценарии P0 (С-01…С-04) проходят приёмочные критерии раздела 4 на golden set.
2. Метрики раздела 13.2 достигнуты: точность цитирования ≥ 99 %, F1 извлечения ≥ 0,95/0,85, 0 галлюцинированных ссылок в выборочном аудите 200 ответов.
3. Журнал аудита позволяет восстановить полную цепочку по любому документу (запрос → источники → правки → подпись).
4. Пройдено тестирование на проникновение, устранены критичные уязвимости.
5. Документация: инструкция инженера (≤ 20 страниц), регламент работы с агентом, инструкция администратора.
6. Обучение: ≥ 5 инженеров прошли, ≥ 90 % выполняют сценарий КС-2 самостоятельно.

## 16.2 Критерии успешности пилота (go/no-go)

| Критерий | Порог |
|---|---|
| Сокращение времени на КС-2 | ≥ 3× (цель 5–10×) |
| Доля документов, принятых без правок | ≥ 60 % |
| Возвраты пакетов ИД от технадзора | Снижение ≥ 30 % |
| Инженеры используют систему добровольно (не по приказу) | ≥ 80 % целевых пользователей, ≥ 3 сценария в неделю |
| Экономический эффект | Подтверждён расчётом по факту 1 месяца пилота |
| Инциденты ИБ | 0 критичных |

## 16.3 Чек-лист пилота

- [ ] Выбран объект с активной фазой СМР и потоком ИД
- [ ] Собрано 50–100 пакетов документов, подписано соглашение о конфиденциальности
- [ ] Размечен golden set (≥ 30 актов, ≥ 200 нормативных вопросов)
- [ ] Определены ответственные: инженер-пользователь, эксперт-эталон, ИТ-сопровождение
- [ ] Настроены шаблоны КС-2/АОСР заказчика, матрица комплектности
- [ ] Проведён базовый хронометраж «до»
- [ ] Зафиксированы правила HITL и порядок эскалации
- [ ] Настроен журнал аудита и доступ для ИБ
- [ ] Определены даты еженедельного разбора ошибок

# Приложение F. Правила приоритета и конфликтов нормативных документов

1. Действующий СП/ГОСТ приоритетнее СНиП и отменённых документов.
2. Специальный документ приоритетнее общего (СП по конкретному виду работ > общий СП).
3. Требования договора/технического задания заказчика могут быть строже норм, но не мягче.
4. При конфликте норм агент не выбирает самовольно: выводит оба варианта с реквизитами и эскалирует на «Нормативщика»/человека.
5. Дата применимости: проверка по редакции, действовавшей на дату документа; факт указывается в ответе.
6. Отменённая норма может упоминаться только с явной пометкой «отменён» и ссылкой на замену.
