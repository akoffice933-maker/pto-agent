# Смежные проекты: что берём, что нельзя и как стыковать

Документ к этапу «сметное расширение»: разбор открытых проектов по сметам и обмерам,
которые нам присылали как ориентиры. Цель — не «сделать как у них», а понять, какую часть
нашего контура они закрывают лучше нас, и не наступить на лицензию.

Данные о звёздах и лицензиях сверены с GitHub API **2026-11-03** (`scripts/check_analogues.py`),
машиночитаемый список — `data/reference/analogue_projects.json`, проверка политики — `tests/test_analogues.py`.

## 2. Главное правило: лицензия сильнее звёзд

Наш репозиторий — **MIT**, поэтому:

| Лицензия проекта | Код копировать | Что можно | Что нельзя |
|---|---|---|---|
| MIT / Apache-2.0 / BSD | да, с уведомлением об авторстве | брать функции, схемы, тесты | убирать copyright |
| **AGPL-3.0** (bidwright, opentakeoff) | **нет** | читать как идею; подключать как **отдельный сервис**, который поднимает сам пользователь | вставлять код, промпты, схемы в наш пакет — AGPL «заразит» всю поставку |
| **нет лицензии** | **нет** | читать код, формулировать свою реализацию | любое копирование: по умолчанию все права защищены |
| **NOASSERTION** (база CWICR) | зависит от данных | использовать как источник расценок **после** ручной проверки условий | тащить базу в репозиторий «по умолчанию открытая» |

Три вопроса перед тем, как взять чужой фрагмент:

1. **Лицензия кода** разрешает производную работу в MIT-проекте? (AGPL и «без лицензии» — сразу нет.)
2. **Лицензия данных** отдельная? (база расценок — это данные, а не код; у CWICR статус NOASSERTION.)
3. **Мы берём идею или текст?** Идею («этап review отдельным шагом») переписываем своими словами и своим кодом; текст промптов и схемы — это тоже объект авторского права.

Практика: раз в квартал `python3 scripts/check_analogues.py` — он сверит звёзды и, что важнее,
**лицензии**, и упадёт с кодом 2, если кто-то в списке «разрешил копировать AGPL».

## 3. Что реально берём — три сценария

### 3.1. Обмер как внешний MCP-сервер (opentakeoff, estimaite-mcp)

У нас 14 MCP-инструментов, и обмер упирается в то, что мы умеем мерить **свой** DXF и **свой**
скан. Чужие форматы (PDF, Revit-экспорт, IFC «как есть») — не наша сила, и писать свой
PDF-обмер значит потратить месяц на то, что уже сделано.

Схема, которая не нарушает AGPL:

```
наш MCP-клиент (Claude Desktop / Cursor / VS Code)
        │
        ├── pto-agent mcp (17 инструментов, MIT)      ← наш код
        └── opentakeoff / estimaite (AGPL, чужой процесс)
                    │
                    └── возвращает объёмы по помещениям и видам работ
```

Наш модуль сверки (`takeoff` + `reconcile`) получает второй, независимый источник объёмов:
расхождение «наш DXF ↔ их PDF-обмер» — это уже не спор с подрядчиком, а проверка исходных данных
до выпуска. В демо-контуре это дало бы ответ на вопрос, который сейчас решается вручную:
почему по смете 174 752 000 ₽, а по журналу объёмов на 21 271 000 ₽ меньше.

Что нужно сделать: адаптер `pto_agent/cad/external_takeoff.py`, который вызывает чужой MCP по
stdio/http и приводит ответ к нашей схеме `takeoff` (handle, code, qty, unit). Никакого импорта
их кода — только JSON по протоколу.

### 3.2. База расценок ГЭСН/ФЕР (OpenConstructionEstimate-DDC-CWICR)

Наш «деньги под риском» считает рубли по ценам **нашей** сметы. Если позиции в смете нет
(новая работа, допсоглашение), сейчас честно пишем «не оценено». База на 55k+ позиций закрывает
именно этот случай: подтянуть расценку по коду и показать вилку «по смете / по базе».

Порядок: (1) проверить условия базы вручную, (2) положить в `data/` только индексы, а не всю базу,
(3) при недоступности базы или отсутствии позиции — снова «не оценено», а не 0 ₽. Правило
«не оценено ≠ 0» уже зафиксировано в документе 08, его и держимся.

### 3.3. Паттерны архитектуры (MIT-проекты)

- **QTO → Pricing → Validation** (DDC_Skills): у нас роли уже разделены (`vision` → `plan`/`takeoff` → `impact`), не хватает явного **валидатора плана** до применения — частично это `validate_operations`, но проверок на «объём против базы» там нет.
- **Review как отдельный этап** (bidwright): у нас `commit` требует подтверждения человека, но нет отчёта «что проверено, что осталось». Кандидат на 15-й MCP-инструмент — `review_summary`.
- **Формат skill** (DDC_Skills): «когда вызывать, входы, выходы, критерий успеха» — переносим в описания инструментов и промпты.
- **GO/NO-GO по марже** (chance-electro): у нас есть «деньги под риском» со стороны заказчика; вердикт подрядчика («идти на этот объём или нет») — естественное продолжение для режима «мой объект».
- **Смета как аудит с перечнем нарушений** (costing-master): наш `norms` уже отвечает с цитатой на пункт СП; не хватает сводного отчёта «все нарушения по смете одним списком».

## 4. Чего сознательно не делаем

| Соблазн | Почему нет |
|---|---|
| Взять bidwright/opentakeoff как основу | AGPL-3.0: наш MIT-репозиторий и поставка «одной командой» перестанут быть MIT |
| Заменить наш офлайн-CV на YOLO (Construction-AI-Agent) | офлайн-детектор не требует обучения, объясним по пикселям и работает на CPU; YOLO вернёт «чёрный ящик» без гарантии полноты |
| Свой оркестратор (CrewAI/LangGraph) | у нас оркестратор — MCP-клиент пользователя; свой слой добавит зависимость и точку отказа |
| Встроить базу расценок в git | 330 МБ демо-сканов уже показали цену тяжёлых артефактов; база — внешний источник, не поставка |

## 6. Как поддерживать список

```bash
python3 scripts/check_analogues.py --offline   # структура и политика (без сети, CI-режим)
python3 scripts/check_analogues.py             # сверить звёзды и лицензии с GitHub API
python3 scripts/check_analogues.py --write     # обновить JSON после проверки
python3 -m pytest tests/test_analogues.py -q   # 10 тестов политики
```

Скрипт печатает таблицу, отдельно — лицензионные ограничения и расхождения с GitHub; при
нарушении политики копирования возвращает код 2. Тесты проверяют то, что важнее данных:
AGPL и проекты без лицензии **никогда** не помечены как «можно копировать», у каждого MIT-проекта
описано, что именно берём и что не берём, а подмена флага ломает сборку.
