## Исправления (2026-11-22, после аудита)

Все подтверждённые находки 1–7 исправлены; PoC инвертирован в регрессионные тесты.

1. **IDOR чтение заявок:** `_requests_view` фильтрует строки по `_object_visible`
   (новая функция: область «own» — только свои объекты; «all»/«none» на чтение не
   ограничиваются — сервисный актор читает всё, запись ему запрещена правами и
   `_require_human`). Дашборд `/` фильтрует `open_requests` тем же предикатом.
2. **IDOR запись:** `request_approve`/`request_reject`/`request_pay` вызывают
   `_require_object` по объекту заявки до мутации → `403 OBJECT_FORBIDDEN`.
3. **IDOR склад:** `_check_warehouse_allowed` вызывается всегда в `/warehouse` и
   `/warehouse/table` (раньше — только при `?warehouse=` и только в `/warehouse`).
4. **MCP чтение:** `check_paths` покрывает `summary_source`, `norms_dir`, `paths`,
   массивы `*_paths` (итерация по спискам), `prices_dir` (write), `base_dir`
   (корень инструментов обязан быть внутри песочницы); пути внутри манифеста
   `scan_release_batch` проверяются при включённой песочнице.
5. **MCP запись:** `sheet_id` в `process_sheet` санитизируется до basename
   (путь кэша листа не может выйти за `out_dir/sheets`).
6. **Open redirect:** `next` после логина обязан начинаться с ровно одного `/`
   (без `//` и без `\`).
7. **Login/logout CSRF:** форма входа получила скрытое поле `csrf`, `login_submit`
   и `logout` проверяют токен через `_check_csrf`.

**Остаточные риски / не исправлялось (не подтверждено PoC):**
- Относительные пути MCP-инструментов разрешаются от CWD процесса, а `check_paths`
  валидирует от `base_dir`: при запуске сервера с CWD ≠ `base_dir` возможна
  запись/чтение вне песочницы. Рекомендация: запускать сервер с CWD = `base_dir`
  либо разрешать пути в инструментах через `safe_path`.
- Вложенные пути в inline-`config` (`object_pack.sections.*.sources`) не покрыты
  `check_paths` (только top-level аргументы).
- Агрегаты сводки на дашборде (`store.summary`: суммы по складу/казначейству) —
  общефирменные итоги без привязки к объектам; строки заявок фильтруются.
- Неподтверждённые кандидаты из раздела ниже (netguard redirect, конкурентная
  запись Store, auth hardening) — без изменений, требуют отдельных PoC.

## Подтверждённые находки

### 1. Нарушение object-scope: чтение чужих заявок (IDOR, read) — High

Роли с scope `own` (прораб, снабженец, ПТО) по матрице `data/reference/rbac.json`
не должны видеть чужие объекты. Однако `_requests_view` вычисляет `visible`, но
добавляет в результат все строки; шаблоны рендерят все переданные rows.
Подтверждено на `/requests`, `/requests/table` и `/` (дашборд показывает первые
заявки казначейства без фильтра): контрагент чужого объекта (`AUDIT-PRIVATE-COUNTERPARTY`)
присутствует в ответе для пользователя, у которого объект не закреплён.

### 2. Нарушение object-scope: запись по чужим заявкам (IDOR, write) — High

`POST /requests/{number}/approve` и `/reject` проверяют только право ступени маршрута
и CSRF, но не `_require_object`. Снабженец, у которого закреплён только объект A,
успешно согласовал и отклонил заявку объекта B (`З-002`): изменение `approvals`/`status`
сохранилось в `treasury/state.json`. Это не просто «видит» — это изменение финансового
документа чужого объекта.

### 3. Нарушение object-scope: склад без фильтра склада (IDOR, read) — Medium

`GET /warehouse` проверяет объект только при переданном `?warehouse=...`; без query
показывает все остатки/документы. `GET /warehouse/table` не проверяет scope вообще.
Подтверждено differential-тестом: тот же чужой склад с фильтром даёт
`403 OBJECT_FORBIDDEN`, без фильтра — `200` с данными чужого объекта.

### 4. MCP sandbox: чтение вне базового каталога — Medium

`check_paths` проверяет только top-level ключи, оканчивающиеся на `_path` и входящие
в `WRITE_PATH_KEYS`. Аргумент `summary_source` (инструмент `asbuilt_docs`, kind=`spec`)
не покрыт: `load_positions` открывает его напрямую через `Path(...)` без `safe_path`.
Подтверждено: `smeta_path` вне sandbox отклоняется, а тот же файл через `summary_source`
читается и его содержимое возвращается в ответе инструмента.

### 5. MCP sandbox: перезапись файла вне базового каталога — High

`scan_release_batch` принимает манифест с `sheets[].sheet_id`. `process_sheet` пишет
кэш в `out_dir/sheets/{sheet_id}.json` без нормализации: абсолютный `sheet_id`
(например, путь к временному файлу вне `base_dir`) приводит к перезаписи этого файла
JSON-записью листа — даже при ошибке чтения чертежа (запись происходит до/вне зависимости
от успеха обработки). Подтверждено: файл вне sandbox перезаписан, исходное содержимое
утрачено, `isError=False`. Требуется санитизация `sheet_id` (только basename/allowlist)
и проверка итогового пути через `safe_path(..., write=True)`.

### 6. Open redirect после логина — Low

`POST /login` берёт `next` из query и допускает всё, что начинается с `/`, включая
`//audit.invalid/landing` (protocol-relative URL). Подтверждено: `Location:
//audit.invalid/landing` в 303-ответе. Кражи cookie не происходит (домен не меняется),
но возможен фишинг после легитимного логина. Рекомендация: разрешать только пути,
начинающиеся с ровно одного `/` и не содержащие `//` в начале, либо allowlist маршрутов.

### 7. Login CSRF — Low

Логин не использует CSRF-guard: POST с чужим `Origin`/`Referer` и без предшествующей
сессии успешно создаёт сессию. Подтверждено локально. Эксплуатация ограничена
(атакующий логинит жертву в свою учётную запись), но guard на логин/выход
рекомендуется добавить.

## Проверено, уязвимостей не подтверждено (контрольные тесты)

- **Агент (ИИ) не может писать:** POST `/closing` от роли agent → `403 AGENT_FORBIDDEN`,
  состояние не изменено.
- **CSRF на бизнес-POST работает:** неверный токен → `400 CSRF`, состояние не изменено.
- **XSS экранируется:** Jinja2 autoescape; payload в контрагенте рендерится как
  `&lt;img ...&gt;`, не как HTML. Отражённый/сохранённый XSS в проверенных экранах не найден.
- **MCP HTTP:** токен обязателен, non-loopback без токена не стартует, CORS allowlist,
  `compare_digest`; `/health` и `/tools` публичны по дизайну (не auth bypass).
- **Пароли:** PBKDF2-SHA256, 200k итераций, случайная соль, `hmac.compare_digest`;
  пользователь перезагружается на каждый запрос (отключение учитывается сразу).
- **LLM:** provider-policy check, запрет env-override endpoint для personal/commercial_secret.
- **Demo-учётки:** публичные demo-пароли — намеренно, не находка.

## Неподтверждённые кандидаты (требуют отдельного PoC, не заявлять как баги)

- `netguard`: проверка literal hostname без DNS IP; `_SameHostRedirect` сравнивает только
  hostname (не scheme/port) и не revalidates redirect — возможен downgrade/port trust,
  но без callback/read impact не подтверждён.
- `Store`: state загружается до `with store.lock` в writes — возможна потеря обновлений
  при конкурентной записи; многопроцессная защита отсутствует. Без concurrent PoC не заявлять.
- Auth hardening: `https_only=False`, различение unknown/disabled/password при логине,
  доверие `X-Forwarded-For` в аудите IP. Низкий приоритет, hardening, не подтверждённые уязвимости.
- Зарплата видна всем ролям — по дизайну (см. rbac.json), не баг сам по себе.
- `/pay` без object-check: бухгалтер имеет scope `all`, поэтому не баг.

## Ограничения аудита

- Первый проход: веб-интерфейс, RBAC/сессии, MCP/ИИ-границы. Не проверялись: реальные
  внешние сервисы, production-данные, сетевой периметр, зависимости на CVE (pinned-версии
  не сверялись с advisory-базами), браузерный рендер XSS (только серверный вывод).
- PoC — локальные, на временных данных; эксплуатация в production не тестировалась.
- BugHunter — prompt/checklist bundle, не автоматический сканер: методология применялась
  вручную, полнота покрытия чек-листов не гарантируется.
