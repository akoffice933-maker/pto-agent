# MCP-обвязка: подключить агента ПТО к Claude Desktop, Cursor и VS Code

**Версия:** 0.6.0 · **Дата:** 03.11.2026 · **Протокол:** Model Context Protocol 2025-06-18

Сервер уже был; этот шаг делает его **подключаемым**: одна команда установки, готовые
конфиги для трёх клиентов, HTTP-транспорт в контейнере, тесты самого протокола.
После установки инженер открывает чат в своём клиенте и говорит «сколько стоит спор по
акту №38» — агент вызывает `assess_release_impact` и отвечает цифрой из сметы.

---

## 1. Что подключается

| Параметр | Значение |
|---|---|
| Имя сервера | `pto-cad` (меняется флагом `--name`) |
| Команда | `python3 -m pto_agent.mcp_server --base-dir <папка проекта>` |
| После `pip install -e .` | `pto-mcp` (та же команда короче) |
| Транспорты | `stdio` (клиенты) и `http` (`POST /mcp` + инспектор `GET /`) |
| Инструментов | **14** |
| Протокол | `2025-06-18`, capabilities: `tools` |
| Санити-проверка | `GET /health` → `{"status":"ok","tools":17}` |

## 2. Установка в один шаг

```bash
pip install -r requirements-pto.txt      # или: pip install -e .
python3 scripts/install_mcp.py --client claude --write    # Claude Desktop
python3 scripts/install_mcp.py --client cursor --write    # Cursor (~/.cursor/mcp.json)
python3 scripts/install_mcp.py --client vscode --write    # VS Code (.vscode/mcp.json)
python3 scripts/install_mcp.py                            # просто напечатать конфиг
```

Установщик делает четыре вещи, которые обычно ломают интеграцию руками:

1. **Подставляет реальный путь** к папке проекта и к интерпретатору (не `python`, а тот,
   в котором стоят зависимости).
2. **Не затирает чужие MCP-серверы** — вливает свой ключ в существующий конфиг.
3. **Делает резервную копию** (`*.bak-20261103-134500`) перед изменением.
4. **Знает различия клиентов**: у VS Code ключ `servers` и обязательный `type: "stdio"`,
   у Claude Desktop и Cursor — `mcpServers`.

Файлы конфигов лежат в `mcp/`: `claude_desktop_config.json`, `cursor_mcp.json`,
`vscode_mcp.json`, `http_server.json` — их можно скопировать руками, если установщик
не подходит под вашу ОС.

## 3. Конфиг, который получается

```json
{
  "mcpServers": {
    "pto-cad": {
      "command": "/usr/bin/python3",
      "args": ["-m", "pto_agent.mcp_server", "--base-dir", "/opt/pto-agent"],
      "env": {
        "PTO_MCP_BASE_DIR": "/opt/pto-agent",
        "PTO_MCP_AUDIT": "out/cad/audit.jsonl"
      }
    }
  }
}
```

Настройки берутся и из окружения — удобно для контейнеров и CI:

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `PTO_MCP_BASE_DIR` | текущая папка | рабочая папка проекта (пути в инструментах относительные) |
| `PTO_MCP_AUDIT` | `out/cad/audit.jsonl` | журнал аудита вызовов |
| `PTO_MCP_TRANSPORT` | `stdio` | `stdio` или `http` |
| `PTO_MCP_HOST` / `PTO_MCP_PORT` | `0.0.0.0` / `8765` | адрес HTTP-транспорта |

Явный флаг в командной строке важнее переменной окружения — это закреплено тестом.

## 4. HTTP-транспорт и контейнер

```bash
# локально
python3 -m pto_agent.mcp_server --transport http --port 8765
# инспектор: http://localhost:8765/   health: /health   список: /tools

# в контейнере
docker build -t pto-agent-mcp:0.6 .
docker run -d -p 8765:8765 -v "$PWD/out:/app/out" pto-agent-mcp:0.6
# или: docker compose -f mcp/docker-compose.yml up --build
```

В образе только сервер и зависимости; модель (Qwen2.5-VL + vLLM) разворачивается отдельно
в контуре заказчика — это то же решение, что и в остальном проекте: инференс не едет
в поставке.

## 5. Что умеет агент через MCP (17 инструментов)

| Группа | Инструменты | Зачем инженеру |
|---|---|---|
| Чтение | `get_drawing_info`, `cad_validate_template`, `cad_takeoff`, `cad_diff` | «что на чертеже», «шаблон соблюдён?», «объёмы», «что изменилось» |
| Пометки | `scan_redline_image`, `analyze_redline`, `plan_from_scan_redline`, `validate_operations`, `apply_operations` | скан → пометки → план правок → проверка → применение **с подтверждением** |
| Выпуск | `scan_release_batch` | 30–50 листов за один вызов со сводкой |
| Деньги | `assess_release_impact` | споры в рублях: по одному акту (`batch_path`) или по портфелю (`acts_path`) |
| Итог проверки | `review_summary` | «что проверено, что осталось, где нужно решение человека и можно ли подписывать» одним ответом (или готовым markdown) |
| Исполнительная документация | `asbuilt_docs` | генерация, а не проверка: схема из DXF (DOCX + PNG), АОСР по РД-11-02-2006, реестр ИД (XLSX) или проверка комплектности; параметр `kind`: scheme / aosr / registry / check |
| Внешний обмер | `external_takeoff` | чужой MCP-обмер (PDF, экспорт из BIM) → наши позиции и сверка с нашим обмером/сметой; код внешнего сервера не встраивается |
| Служебные | `export_scheme`, `cad_list_operations`, `cad_history` | схема, список и история операций |

Пример диалога:

> — Сколько денег под риском по объекту?
> — *вызов `assess_release_impact` с `acts_path`* → 3 акта, покрытие 100 %, под риском
> 2 091 000 ₽ (5,43 % проверенного), из них 24 800 ₽ недополучено.

## 6. Безопасность: почему агенту можно это доверить

1. **Чертёж не меняется без человека.** `apply_operations` в режиме `commit` требует объект
   `confirm {by, role, comment}`; без него — только план. Это проверяется тестом схемы.
2. **Каждый вызов пишется в журнал аудита** (`out/cad/audit.jsonl`, append-only, хэш-цепочка).
3. **Модель не придумывает числа.** Координаты, объёмы и цены берутся из файлов; в ответах
   инструментов есть пометка `note` об источнике.
4. **Ошибка инструмента — это ответ, а не падение.** Сервер отдаёт `isError: true` с текстом;
   JSON-RPC-ошибки зарезервированы под неизвестный метод (`-32601`) и неизвестный инструмент
   (`-32602`), битый JSON — `-32700`.
5. **stdout чистый.** В stdio-транспорте в stdout идёт только JSON-RPC; всё служебное — в stderr.
   Нарушение этого правила — самая частая причина «клиент не видит инструменты».

## 7. Что проверено тестами (15)

| Что | Как проверяется |
|---|---|
| Рукопожатие | `initialize` → `protocolVersion`, `serverInfo`, capabilities; нотификация `initialized` без ответа |
| Список | `tools/list` — ровно 17 инструментов, ожидаемые имена на месте |
| Вызов | `tools/call get_drawing_info` возвращает факты из DXF (единицы, штамп, объёмы) |
| Ошибки | неизвестный метод `-32601`, неизвестный инструмент `-32602`, битый JSON `-32700`, ошибка инструмента — `isError` |
| Чистота канала | каждая строка stdout — валидный JSON-RPC |
| Схемы | у всех инструментов `type: object`, `properties`, `required ⊆ properties` |
| Подтверждение | у `apply_operations` есть `confirm{by,role,comment}`, в описании — «подтверждение» |
| HTTP | `/health`, `/tools`, `POST /mcp`, batch-запросы, инспектор, CORS |
| Окружение | `PTO_MCP_*` собираются в аргументы, флаг важнее переменной |
| Установщик | печать конфига, слияние без потери чужих серверов, резервная копия, http-вариант |

## 8. Ограничения

1. **Нет авторизации в HTTP-режиме.** Для локальной работы это норма; для сети — ставьте
   за reverse-proxy с токеном или используйте stdio. В контейнере порт открыт наружу только
   по вашему решению.
2. **Сервер однопоточный по состоянию проекта.** Параллельные `apply_operations` на один
   файл не поддерживаются: операции применяются последовательно.
3. **Пути в инструментах — относительно `base-dir`.** Это осознанно: агент не должен выходить
   за папку проекта.
4. **MCP 2025-06-18.** Более новые версии протокола появятся — `protocolVersion` в одном месте.
5. **SDK не используется.** Сервер написан на stdlib: меньше зависимостей в поставке, но новые
   возможности протокола (sampling, roots) придётся добавлять руками.
