## 1. Смету АРОС агент теперь читает напрямую

Новый модуль `pto_agent/asbuilt/aros.py`:

```
python3 -m pto_agent asbuilt smeta --smeta uploads/smeta_1166N_AROS.md
python3 -m pto_agent asbuilt acts  --smeta uploads/smeta_1166N_AROS.md \
        --act-prefix "АОСР-1166/Н" --write-specs --out out/asbuilt/1166n
```

Что учитывает разбор:

* шапка таблицы (графы 1…12) — не позиция: раньше «3» попадала в работы;
* `colspan` в выгрузке сдвигает графы — единица и объём читаются из правильных ячеек
  («100 м», «0,4», «1000 м», «0,3264»);
* формула объёма (`V=320*1,02/1000`) вынимается из наименования в отдельное поле;
* строки ресурсов под позицией (ОТ, ЭМ, машины, `1-100-23`) позициями не считаются;
* **позиция с кодом ресурса — материал, а не работа** (см. п. 2);
* разделы сохраняются: смета режется по разделам и группам, а не «в один акт».

Чего модуль не делает: **нативный `.docx` и PDF АРОС он не читает** — нужна выгрузка в
html/markdown (то, что вы прислали) либо xlsx. Для docx нужен образец файла, чтобы не
гадать со структурой.

## 2. Главная содержательная находка: материалы ≠ работы

В смете кабель, кабель-канал, распаечные коробки, автоматы и УЗО идут **отдельными
строками с кодами ФГИС ЦС**. Если считать их работами (как делал прежний прогон):

* в акт попадает «прокладка кабеля», которой в смете нет;
* доля электромонтажа считается по материалам, то есть неправильно;
* объёмы в акте задваиваются.

Сейчас: `kind: work` — 33 позиции, `kind: material` — 14. Материалы не классифицируются,
но не теряются: они складываются по коду (ВВГнг 3х1,5 встречается дважды → одна строка,
объём 0,3754) и попадают в **перечень материалов того акта**, к которому относятся:

| Акт | Материалы сметы |
|---|---|
| Борозды | — (раствор внутри расценки) |
| Проходки | трубы стальные бесшовные 32×2,8 — 3,09 м |
| Щиты | автомат 1P 16 А C — 20 шт; УЗО 2P 25 А 30 мА — 3 шт |
| Освещение | — |
| Кабельные трассы | ВВГнг 3х1,5 / 3х2,5 / 3х4; кабель-канал 25×25 и 40×25; распаечные и ответвительные коробки; ПуГВ 1х4 |

Реквизиты документов о качестве остаются `needs_input` — их берут из входного контроля.

## 3. Классификатор на реальных формулировках: 33 из 33

Прежний прогон узнавал 23 из 47 (по вашей оценке). На этой смете после доработки —
**33 из 33 работ, `unknown` пуст**. Что добавилось в матрицу (без правки кода):

| Формулировка сметы | Ключ | Куда попадает |
|---|---|---|
| «Прибор или аппарат» (ГЭСНм08-03-575-01) | `прибор или аппарат` | electrical → акт «Щиты» |
| «Рукав металлический наружным диаметром до 48 мм» | `рукав металлическ` | electrical → «Проходки, гильзы» |
| «Сверление отверстий в строительных конструкциях из кирпича» | `сверление отверсти` | electrical → «Проходки» |
| «Перевозка грузов I класса автомобилями-самосвалами» | `перевозка груз` | waste_removal (вне актов) |
| «Коробка ответвительная/распаечная» | `коробк` | electrical |

Плюс две ошибки разбивки, которые нашлись только на этом файле:

* **«Труба гофрированная ПВХ для защиты проводов» уезжала в щиты** — в группах актов
  подстрока искалась без границы слова, и «защиты» совпадало с «щит». Теперь группы
  используют тот же поиск с начала слова, что и классификатор;
* **«Розетка … при открытой проводке» уезжала в кабельные трассы** («провод»), потому что
  трассы шли раньше освещения. Порядок групп стал: борозды → проходки → **щиты →
  освещение** → трассы → заземление → ПНР.

## 5. Второе содержательное исправление: приложения и протоколы — по группе, а не по виду работ

Было: акт на борозды прикладывал протоколы изоляции, «фаза-нуль», УЗО, заземления и
освещения — потому что комплект брался по виду работ «электромонтаж» целиком. Это и было
вашим замечанием про лишние протоколы.

Стало: у каждой группы актов свой комплект (`required`) и свои протоколы (`protocols`):

| Акт | Протоколы в акте | Комплект документов |
|---|---|---|
| Борозды | — | АОСР, схема, сертификаты, журнал |
| Проходки | — | АОСР, схема, сертификаты, журнал |
| Щиты | УЗО; петля «фаза-нуль» | + протокол |
| Освещение | испытание осветительной установки | + протокол |
| Трассы | изоляция; петля «фаза-нуль» | + протокол |
| Заземление | сопротивление заземляющего устройства | + протокол, акт испытаний |
| ПНР | все пять | полный комплект |

Валидатор теперь проверяет приложения по комплекту акта (`required_kinds` в спецификации),
а не по виду работ — иначе акт на борозды требовал бы акт испытаний электроустановки.

## 6. Нормы: ПУЭ проверяется, но честно — «фрагментом»

Появилась рабочая нормативная база `data/norms/` (демо-база `data/demo/norms` подключается
автоматически, если в рабочей нет документа). Добавлен `pue_7_1_8.md` — ПУЭ-7, гл. 1.8,
**пп. 1.8.37 и 1.8.39**, статус `fragment`.

```
ПУЭ, 7-е изд. п. 1.8.37            → verified_partial («пункт есть фрагментом, полный текст не загружен»)
ПУЭ, 7-е изд. п. 1.8.39            → verified_partial
СП 76.13330.2016 п. 6.1            → doc_missing (не проверено)
ГОСТ Р 50571.16-2019 п. 61.3       → doc_missing
СП 256.1325800.2016 п. 14.1        → doc_missing
```

То есть ваши два пункта ПУЭ мы **проверили по тексту главы**, а не «по памяти», но полного
документа в базе нет — и агент пишет именно это, а не «подтверждено». Чтобы три оставшихся
документа стали `verified`, их нужно положить в `data/norms/` (формат — `data/norms/README.md`).

Нормы в спецификации помечены `source: matrix`, в акт попадают с номером пункта и редакцией.
