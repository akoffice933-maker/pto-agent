# 17. OSS-проекты под расширение pto-agent в платформу стройфирмы

Поиск по GitHub под слои 2–9 из предложенного плана. Всё, что ниже, **проверено машинно**, а не
взято из памяти: для каждого проекта через GitHub REST API запрошены звёзды, дата последнего
коммита, язык и лицензия (`/repos/{owner}/{repo}`, `/repos/{owner}/{repo}/license`), у спорных
случаев прочитан файл `LICENSE` целиком. Дата проверки — **2026-11-05**.

Реестр: `data/reference/platform_oss.json` (43 проекта, 9 слоёв).
Проверка: `python3 scripts/check_platform_oss.py --offline` (в CI — только она, без сети).

Главный вывод, если коротко: **готового OSS под российский стройучёт нет** — ни сметы, ни КС-2,
ни реестра подрядчиков. Зато есть отличные «полуфабрикаты» для отдельных кусков: склад, Гантт,
аудит-лог, 1С-обмен, полевые наряды. Их и надо брать, а ядро ПТО оставить своим.

### Слой 3 — закупки и снабжение (6)

`erpnext` (GPL-3.0, 40 962★) — эталон процесса «заявка → запрос КП → сравнение → заказ»;
`odoo` (LGPL-3.0) — процессы закупки и полевых работ; **`InvenTree` (MIT)** — единственный, чей
код реально можно взять; `openprocurement.api` (Apache-2.0) — схема оферты; `leihs` (GPL) и
`openboxes` (EPL) — идеи учёта инструмента и складских операций.

### Слой 4 — подрядчики и субподряд (2)

Слабое место OSS: специализированного реестра подрядчиков с рейтингом **нет**. Берём:
`ProjectEngine` (GPL, идеи) — «задача зависит от задачи», прогресс и просрочка по цепочке — это
и есть основа оценки исполнения субподрядчиком; `openprocurement.api` — перечень документов
допуска (СРО, НРС, персонал). Сам реестр пишем свой, как и КС-2.

### Слой 5 — финансы и казначейство (3)

`firefly-iii` (AGPL, 25 074★) — правила категоризации платежей и «остаток с учётом
запланированного» (это и есть кассовый разрыв); `actual` (MIT) — «конверты» и синхронизация;
`invoiceplane` — модель «счёт → частичные платежи → остаток». У InvoicePlane ядро MIT, но
`LICENSE.txt` **запрещает перепродажу и распространение приложения** и использование имени —
поэтому в реестре `copy_allowed: false`, только идеи.

### Слой 6 — управление проектом (4)

`openproject` (GPL-3.0, 17 006★) — модель «базовый план vs факт» и типы связей FS/SS/FF; берём
как внешний сервис или идеи. `frappe/gantt` (MIT) — встраиваемый виджет. `ProjectEngine` — CPM из
зависимостей. `taiga-back` (MPL-2.0) — схема API «история → задача → комментарий».

### Слой 7 — CRM и коммерция (4)

`krayin/laravel-crm` (MIT, 24 109★) и `Django-CRM` (MIT) — модели лида/сделки; для нас важнее
второй: Python-стек, идеи переносятся напрямую. `bidcraft` (**Apache-2.0**) — «разобрать ТЗ на
требования → проверить, что каждое закрыто» — это же нужно для тендерного модуля. `espocrm`
(AGPL) — идея сущностей на метаданных.

### Слой 8 — мобильное приложение и поле (4)

`OCA/field-service` (AGPL) — наряд-заказ с чек-листом и фото до/после; `WatermelonDB` (MIT) и
`PowerSync` (Apache-2.0) — offline-first и синхронизация с конфликтами; `paperless-ngx` (GPL,
47 707★) — приём документа с телефона → OCR → теги → поиск, как внешний сервис.

### Слой 9 — 1С / БИТ.Строительство (6)

`OpenIntegrations` (MIT) — обмен со стороны 1С; `django-cml` (BSD-3) — CommerceML 2 (номенклатура,
цены, остатки) — формат, который 1С понимает; `php-commerceml` (MIT) — коллекция реальных
«сюрпризов» 1С в XML; `python-commerceml` — **без лицензии**, только идеи; `bsl-parser` (GPL) —
разбор кода 1С; `onebase` (MIT) — идея DSL.

### Сквозные (5)

`django-simple-history` (BSD-3) — аудит-лог; `mayan-edms` (Apache-2.0) — карточка документа с
версиями (документ живёт отдельно от акта); `bpmn-js` (MIT) — визуальная схема согласования;
`n8n` и `nocodb` — **Sustainable Use License, не OSI**: код копировать нельзя, только идеи.

## 3. Чего в OSS нет (и не появится)

| Что нужно | Реальность | Что делаем |
|---|---|---|
| Сметы РФ (АРОС, Гранд-Смета, ФСНБ-2022) | Открытого OSS нет вообще. Форматы закрыты, выгрузки — html/xlsx/docx | Свой парсер (уже есть: АРОС-md + xlsx); обмен — по схеме, взятой у pygaeb/OpenConstructionERP как принцип |
| ФГИС ЦС, индексы Минстроя | Открытого API нет; только экспорт и письма с индексами | Импорт из выгрузки + журнал версий цен с датой и источником |
| КС-2, КС-3, АОСР, реестр ИД | Только у нас | Оставляем своим ядром — это и есть отличие |
| Реестр подрядчиков с рейтингом | Нет (только «квалификация» в openprocurement) | Своё: документы + история исполнения + просрочки из графика |
| БИТ.Строительство | Закрытый продукт | Обмен файлами/HTTP + CommerceML, как в наших `sync-1c` |

## 4. Что брать в первую очередь (по этапам плана)

### Этап 1 — «Умное ПТО + деньги» (1–2 месяца)

| Задача | На чём | Оценка |
|---|---|---|
| Импорт смет любых форматов: АРОС, xlsx, PDF | уже сделано (АРОС-md, xlsx); PDF — по образцу, идеи opentakeoff/orama | готово + 1–2 недели на PDF |
| Цены и индексы с журналом версий | идея pygaeb (схема + валидация) | 2 недели |
| «Деньги под риском» по портфелю | уже есть формулы; нужен свод по объектам | 1 неделя |
| Дашборд руководителя | `frappe/gantt` (MIT) как виджет | 1–2 недели |
| Аудит-лог на все действия | `django-simple-history` — схема снимок+дельта | 1 неделя |

### Этап 2 — «Закупки + подрядчики» (2–3 месяца)

Заявки на материалы и сравнение КП — модели берём у `erpnext`/`openprocurement`, склад — **внешним
сервисом InvenTree (MIT)**, а не своим кодом. Реестр подрядчиков — свой: «документы допуска +
история КС-2 + просрочки из графика». Акты от субподряда — генерация уже есть, добавить профиль
подрядчика.

### Этап 3 — «Финансы + проекты» (3–4 месяца)

Акты → платежи: модель частичных платежей из `invoiceplane`, правила категоризации из
`firefly-iii`, прогноз разрыва из `actual` («конверты»). График работ: `openproject` как сервис
или `frappe/gantt` + свой CPM по идеям `ProjectEngine`. 1С — обмен по HTTP/JSON приёмами
`OpenIntegrations` и CommerceML.

### Этап 4 — «Полная фирма»

CRM (идеи `krayin`/`Django-CRM`), полевые наряды (идеи `OCA/field-service` + `WatermelonDB`/
`PowerSync` для offline), архив документов (`paperless-ngx` как сервис, `mayan-edms` как модель),
тендерный модуль (идеи `bidcraft`).

## 5. Лицензионные правила (нарушение = стоп)

| Лицензия | Что можно | Что нельзя |
|---|---|---|
| MIT, Apache-2.0, BSD, ISC | брать код с уведомлением об авторстве | выдавать за своё без уведомления |
| LGPL-3.0, MPL-2.0, EPL-1.0 | ставить отдельной зависимостью/сервисом | копировать код внутрь MIT-пакета |
| GPL-3.0, AGPL-3.0 | читать, брать идеи и схему данных, поднимать внешним сервисом | копировать код в поставку |
| Sustainable Use (n8n, NocoDB) | идеи, внешний сервис у себя | копировать код; это не OSI-лицензия |
| без лицензии | только идеи | любое копирование |
| данные (базы расценок) | смотреть структуру | копировать данные без отдельного согласия |

Проверяется автоматически: `scripts/check_platform_oss.py` возвращает **exit code 2**, если в
реестре появился `copy_allowed: true` при непермиссивной лицензии. Тот же скрипт ловит слой без
единого проекта и расхождение звёзд/лицензии с GitHub.

## 6. Принципы, которые сохраняем при расширении

| Принцип | Как это выглядит в новых слоях |
|---|---|
| Ни одна цифра не выдумывается | КП без даты и срока не сравнивается; цена без источника (ФГИС ЦС, письмо индексов, прайс с датой) не попадает в расчёт; объём без ссылки на лист/позицию не идёт в акт |
| Человек в контуре | Платёж не создаётся из акта автоматически — только предложение с обоснованием; изменение чертежа или цены требует подтверждения |
| Аудит-лог | Схема `django-simple-history`: снимок, дельта, автор, причина — на акты, деньги, цены, реестры |
| MCP-архитектура | Новые слои — новые инструменты (`procurement`, `schedule`, `finance`), а не монолит: каждый вызывается отдельно и возвращает источник данных |

подрядчика строится на наших же данных — КС-2, акты, просрочки.
