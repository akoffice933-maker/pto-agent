## 2. Запуск

```bash
pip install -r requirements-pto.txt          # openpyxl, python-docx, PyYAML, pydantic, pytest, ezdxf
python3 scripts/make_demo_data.py            # сгенерировать демо-смету, журнал, ранее закрытые акты, нормативы
python3 -m pto_agent run --data data/demo --out out
python3 -m pto_agent norms "можно ли включать в акт объёмы сверх сметы"
python3 -m pto_agent approve --out out --by "Иванов И.И." --decision returned_for_revision \
        --comment "Пересчитать позиции 1 и 2 по фактическим АОСР"
python3 -m pto_agent audit-verify --path out/audit.jsonl
python3 scripts/check_expected.py             # сверка с эталоном: 7 из 7 расхождений
python3 -m pto_agent route --intent ks2_validate --data-class commercial_secret --complexity high
python3 -m pytest tests -q
```

Результаты прогона в `out/`:

| Файл | Что внутри |
|---|---|
| `ks2_draft.xlsx` | акт по форме КС-2: шапка, позиции с флагами, итоги, НДС, строки подписей |
| `discrepancies.xlsx` / `.csv` | таблица расхождений с критичностью, значениями, источниками и предлагаемым действием + пустая графа «решение человека» |

| `summary.json` | машиночитаемая сводка (для API/дашборда) |

## 3. Архитектура

```
data/demo/*.xlsx ──► parsers ──► matching ──► reconcile ──┬──► export (КС-2, расхождения, остатки)
     (смета, журнал, акты)      (шифр→название→fuzzy)    │      └──► report.html (руководителю)
                                                          └──► audit (hash-chain JSONL)
data/demo/norms/*.md ──► norms (BM25 + проверка цитаты) ──► citation gate ──► ответ или «не найдено»
config/llm_providers.yaml ──► llm.route() ──► шлюз моделей (OpenAI-compatible), классы данных
```

| Модуль | Ответственность | Ключевое решение |
|---|---|---|
| `pto_agent/parsers.py` | чтение XLSX, нормализация единиц (м³/м3/куб.м) | документы не «понимаются» моделью, а разбираются кодом |
| `pto_agent/matching.py` | сопоставление журнала со сметой: шифр → точное имя+ед. → нечёткое (0,72) | несопоставленная работа не «притягивается» к похожей позиции молча — она попадает в «вне сметы» |
| `pto_agent/reconcile.py` | 7 типов расхождений, дедупликация, остатки | приоритет правил: дубль → объём сверх сметы → повторное закрытие → единицы → отсутствие ИД → вне сметы |
| `pto_agent/norms.py` | мини-RAG по СП с YAML-фронтматтером (designation, edition, status, effective_from) | **нет дословной цитаты — нет ответа**: `cite_verify` сравнивает цитату с текстом пункта посимвольно |
| `pto_agent/export.py` | КС-2, расхождения, остатки в XLSX | суммы пишутся числами, вычисленными кодом, а не формулами-заглушками |
| `pto_agent/report.py` | HTML-отчёт руководителю | все цифры берутся из расчёта, ни одна не вводится вручную |
| `pto_agent/audit.py` | JSONL-журнал с SHA-256 цепочкой | подмена любой записи обнаруживается (`audit-verify`) |
| `pto_agent/llm.py` | маршрутизация по классу данных + OpenAI-compatible вызов | КТ и ПДн не покидают контур; без ключей всё работает детерминированно |
| `pto_agent/cli.py` | `run` / `norms` / `approve` / `audit-verify` / `route` | подписание только человеком |

### Три принципа, которые проверяются тестами

1. **Арифметика — кодом.** Ни один объём, остаток или рубль не вычисляет модель: `test_act_amounts_are_computed_from_quantities`, `test_remainder_formula`.
2. **Цитата или молчание.** Ответ по нормативам выдаётся только с дословной цитатой из указанного пункта указанной редакции; сфабрикованная цитата блокируется (`test_fabricated_quote_fails_verification`), норма, не вступившая в силу на дату проверки, не используется (`test_norm_edition_applicability`).
3. **Решение за человеком.** `approve` не даёт «подписать» акт при открытых критичных замечаниях без письменного обоснования; решение попадает в журнал с хэшем (`approval.json`).

## 4. Что нашёл агент на демо-наборе

| # | Тип расхождения | Шифр | Суть | Критичность |
|---|---|---|---|---|
| 1 | `DUPLICATE` | ФЕР 06-01-001-01 | запись от 12.10 на 160 м³ внесена дважды (один и тот же АОСР-131) | существенное |
| 2 | `VOLUME_OVER_ESTIMATE` | ФЕР 06-01-001-01 | 1 240 м³ против 1 200 м³ по смете (+3,3 %) | критичное |
| 3 | `VOLUME_OVER_ESTIMATE` | ФЕР 06-01-001-02 | 390 м³ против 380 м³ | критичное |
| 4 | `MISSING_BACKING_DOCS` | ФЕР 06-01-001-02 | нет АОСР/исполнительной схемы на 8 346 000 ₽ | существенное |
| 5 | `ALREADY_CLOSED` | ФЕР 16-02-003-01 | закрыто 200 м + выполнено 480 м = 680 м при смете 640 м | критичное |
| 6 | `UNIT_MISMATCH` | ФЕР 11-01-011-01 | в журнале объём бетона в м³, в смете площадь в м² | критичное |
| 7 | `NOT_IN_ESTIMATE` | — | «Устройство отмостки» отсутствует в смете | критичное |

Позиции, оформленные корректно (гидроизоляция, кровля), замечаний не получили — проверяется тестом
на отсутствие ложных срабатываний.

Агент не только фиксирует замечания, но и считает **что можно предъявить**: по позициям без ИД объём
не предъявляется вовсе, по превышению сметы — ограничивается остатком (смета − закрыто ранее).
В черновике КС-2 это отдельные колонки «по журналу» / «к предъявлению» с причиной ограничения.

## 7. Ограничения прототипа (честно)

- Данные **синтетические**: 8 позиций сметы и 11 записей журнала — этого достаточно, чтобы проверить логику, но не чтобы судить о качестве на реальном объекте.
- Нет OCR сканов, нет импорта XML ГГЭ/сметных программ (ГрандСмета, А0, «Барс»), нет КС-3 и АОСР-генератора — это следующий шаг.
- Нет БД: состояние — файлы в `out/`. Схема `db/schema.sql` под это уже написана и ждёт подключения PostgreSQL.
- Нечёткое сопоставление наименований — на `difflib`, без эмбеддингов; на «грязных» реальных сметах потребуется дообучение/эмбеддинги.
- Модель в контуре по умолчанию **не вызывается**: без заданных ключей и доступного vLLM весь прогон детерминированный. Это сделано намеренно — цифры не должны зависеть от модели.

## 8. Дорожная карта следующего этапа

1. **Реальные данные:** импорт смет из ГрандСметы (XML), журналов — из Excel-форм подрядчика; прогон на 1 объекте за прошлый период с ручной сверкой.
2. **CAD:** `ezdxf` в headless-режиме — чтение DXF, проверка соответствия исполнительной схемы объёмам, работа с корпоративными шаблонами (слои, рамки, шрифты), каждое изменение — через подтверждение человеком.
3. **MCP-инструменты:** обернуть `parsers/matching/reconcile/norms` в MCP-сервер (по образцу Autocad-MCP), чтобы агент вызывал их как инструменты с журналированием.
4. **БД и API:** PostgreSQL по `db/schema.sql`, эндпоинты из `api/openapi.yaml`, учёт токенов и стоимости по каждому вызову модели (`llm_call_log`).
5. **Golden set:** прогнать `golden_set/` через пайплайн, посчитать precision/recall по расхождениям и долю проверенных цитат.
6. **КС-3, АОСР, письма:** подключить генерацию DOCX по шаблонам (`python-docx`, `docxtpl` при необходимости).
