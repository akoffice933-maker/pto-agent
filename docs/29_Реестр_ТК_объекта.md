# Реестр технологических карт объекта

**Круг 6.** Было: черновики ТК и ППР писались в `out/tk` файлами, и ответить на вопрос
«что у нас по объекту и что из этого проверено человеком» можно было только открывая каждый
файл. Стало: одна таблица `объект → ТК/ППР → статус → кто проверил` с честным правилом —
подпись действительна только пока содержание совпадает с проверенным.

## 1. Что было не так

Проверено на прошлом круге (23 инструмента, 643 теста): карта собиралась, инженер мог
подтвердить её с ФИО и ролью — но:

1. **файловый каталог не отвечает на вопрос по объекту.** Пять карт одного объекта и одна
   карта другого лежали рядом; статусы («проверено» / «не проверялось») и ФИО нужно было
   вычитывать из каждого JSON;
2. **имя файла было одно на всех.** `tk.write()` всегда писал `tk_draft.json` / `.docx` /
   `.md` — вторая карта в том же каталоге молча затирала первую. Это не гипотеза: при
   подготовке этого круга `concrete` затёр `earthworks`, и в каталоге осталась одна карта из
   трёх;
3. **проверка старела молча.** Отметка `confirmed_by` оставалась в файле при любой правке
   содержания: инженер проверил один текст, а в реестре «проверено» стояло бы на другом.

## 2. Что сделано

**Модуль `pto_agent/tk_registry.py`.** Реестр не спрашивает заново, а читает готовые
черновики (`*_draft`-формат) и собирает по объектам: карта, вид работ, файл, статус, ФИО,
роль, дата проверки, число запросов данных, сверенные нормы, «кого ждём с данными».

**Отпечаток содержания (`tk.content_fingerprint`).** При подтверждении в `confirmed_by`
пишется `content_fingerprint` — sha256 по содержанию черновика без статуса, отметки и
служебных ключей. Реестр сверяет его с текущим:

| Что произошло | Статус в реестре |
|---|---|
| карту никто не подтверждал | `черновик, не проверен` |
| подтверждена ФИО + роль, содержание не менялось | `проверен инженером (не утверждена)` |
| содержание поправлено после проверки | `изменён после проверки — проверка недействительна` |
| в файле есть отметка, но без ФИО/роли | `подтверждение без ФИО — не считается` |

**Стабильные имена файлов (`tk.draft_stem`).** `tk_<вид работ>.json|.docx|.md`,
`ppr_<объект>.json|.docx|.md`. Две карты в одном каталоге больше не затирают друг друга;
подтверждение перезаписывает тот файл, который открыли.

**CLI `pto_agent tk registry`** (`--paths`, `--strict`, код возврата):

```
реестр ТК: объектов 2 · черновиков 7 · проверено инженером 1 · не проверено 6
  · Детский сад на 220 мест: ни одна карта не проверена (ТК 1, ППР 0, запросов данных 5)
  · Школа на 550 мест: часть карт проверена, часть — черновики (ТК 5, ППР 1, запросов данных 33)
  файлы: out/tk/registry.json, out/tk/registry.md, out/tk/registry.xlsx
  реестр показывает состояние черновиков, а не право применять карты на объекте
```

Код возврата: `0` — всё прочитано и подписей-сирот нет; `2` — есть «изменено после проверки»,
проблемы чтения или (с `--strict`) карты без проверки человеком.

**MCP-инструмент `tk_registry` (24-й).** Возвращает `totals`, `objects[]` (состояние,
счётчики, `waiting_for`, карты), `changed_after_confirm`, `not_checked`, `problems`,
`integrity_problems`, `files`, `disclaimer`. Параметр `strict: true` делает провалом карты без
проверки человеком. В схеме инструмента нет параметра `by` — реестр не подтверждает ничего сам.

**Отчёты:** `registry.json` (машинный), `registry.md` (чтение), `registry.xlsx` (лист «Сводка»
+ лист на объект; статусы словами, а не цветом).

## 5. Чего реестр не делает

* **не утверждает карты.** «Проверен инженером» — это отметка о проверке, а не утверждение ТК
  или ППР; утверждает ответственный ИТР, и в отчёте это написано прямым текстом;
* **не восстанавливает утраченное.** Если файл черновика удалён, `verify()` скажет «файла нет
  на диске», но содержание не вернёт;
* **не считает нормы сверенными.** Числа «нормы сверено N из M» берутся из черновиков; в
  текущей нормативной базе проекта сверено 2 нормы из 34 по видам работ — реестр это
  показывает, а не закрашивает;
* **не заменяет журнал аудита.** События `tk.draft_built` и `tk.registry_built` пишутся в
  `audit.jsonl` теми же механизмами (`--audit`), что и раньше.

## 6. Что дальше

1. **Загрузка норм в базу** — 21 документ / 32 пункта из `docs/28`, начиная с СП 70.13330.2012
   (5 пп.), СП 45.13330.2017 (4 пп.), СП 71.13330.2017 (3 пп.): эти три дают 14 из 34 норм
   «сверено».
2. **Реестр по объекту из аудита** — сейчас источник только файлы черновиков; события
   `tk.*` в `audit.jsonl` позволяют показать историю проверок (кто и когда снимал подпись).
3. **Пакетный `--from-dir` с подтверждением по списку** — когда карт десятки, нужен ввод
   проверок из одной таблицы, а не по файлу за раз.

## 7. Воспроизведение

```bash
pip install -q -r requirements-pto.txt
export PYTHONPATH=.

# черновики по объекту
pto_agent tk --out out/tk draft --work-type concrete --object-name "Школа на 550 мест"
pto_agent tk --out out/tk ppr --object-name "Школа на 550 мест"

# проверка человеком (ФИО и роль обязательны)
pto_agent tk --out out/tk confirm --draft out/tk/tk_concrete.json \
    --by "Иванов И.И." --role "главный инженер" --reason "проверка состава операций"

# реестр
pto_agent tk --out out/tk registry            # 0 — чисто, 2 — есть проблемы
pto_agent tk --out out/tk registry --strict   # 2, если есть карты без проверки человеком

python scripts/check_tk_registry.py           # сквозная проверка 5 правил (шаг CI)
env -u PYTHONPATH python3 -m pytest tests -q  # 661 passed
```
