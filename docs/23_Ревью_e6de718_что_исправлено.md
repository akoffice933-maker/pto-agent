## 1. Критичное — исправлено

### 1.1. `NameError` при подтверждённой правке чертежа

**Было.** `cad/mcp_server.py` вызывал `_append_history`, которой не существовало. В режиме
`commit` файл и запись аудита создавались, а клиент получал `NameError` с трейсбеком. Тестов
на commit через MCP не было.

**Стало.** Функция определена: пишет запись истории в `out/cad/history.jsonl` тем же форматом,
что CLI, возвращает путь журнала. Тест `test_mcp_commit_writes_history_and_audit` проходит
полный путь через `handle_rpc` → инструмент → файл + аудит + история.

**Что важно:** дефект был не «косметикой». Подтверждённая человеком правка чертежа
выполнялась, но клиент считал вызов неуспешным — и мог повторить его, получив вторую версию
файла и вторую запись аудита.

### 1.2. `cad/cli.py` не компилировался на Python 3.11

**Было.** Вложенные f-строки с одинаковыми кавычками (`f"{', '.join(f'{k}={v}' ...)}"`) —
синтаксис, разрешённый только с 3.12. CI и README заявляют 3.11.

**Стало.** Внутренняя часть собирается отдельно (`"%s=%s" % ...`). Добавлен тест
`test_package_parses_as_python_311`: он парсит **все** `.py` поставки с
`feature_version=(3, 11)`, то есть закрывает не этот файл, а весь класс таких ошибок.
Дополнительно на момент проверки найдено 0 файлов с синтаксисом выше 3.11.

### 1.3. HTTP-сервер MCP без защиты

**Было.** Привязка по умолчанию `0.0.0.0`, аутентификации нет, CORS `*`, трейсбеки и
абсолютные пути в ответах.

**Стало.**

| Что | Было | Стало |
|---|---|---|
| Адрес по умолчанию | `0.0.0.0` | `127.0.0.1` |
| Сеть без токена | разрешена | `SystemExit` с объяснением |
| Аутентификация | нет | `Authorization: Bearer` (или `X-PTO-Token`), сравнение `hmac.compare_digest` |
| Токен по умолчанию | нет | из `PTO_MCP_TOKEN`; если не задан — генерируется и печатается в stderr |
| CORS | `*` | только явно разрешённый origin (`PTO_MCP_ALLOW_ORIGIN`), иначе заголовка нет |
| `/` (инспектор) | открыт | требует токен |
| Ошибки | тип + текст + трейсбек | тип + текст без путей + `id`; трейсбек — в stderr сервера |

Тесты: `test_http_requires_token` (401 без токена и с неверным), `test_http_has_no_wildcard_cors`,
`test_http_refuses_network_bind_without_token`, `test_http_generates_token_when_missing`,
`test_http_defaults_to_loopback`, `test_public_message_hides_paths`.

### 1.4. Песочница путей

**Было.** Файл вне `base_dir` читался, `out_path` вне корня записывался — тем же вызовом
клиент получал трейсбеки с путями файловой системы.

**Стало.** `safe_path()` разрешает путь и требует, чтобы он оставался внутри корня;
`check_paths()` проверяет **все** аргументы вида `*_path` до выполнения инструмента.

Граница безопасности привязана к транспорту, и это сделано осознанно:

* **`http`** — сервис в сети, песочница чтения и записи включена всегда;
* **`stdio`** — локальный клиент того же пользователя; песочница включается
  `PTO_MCP_SANDBOX=1` или `make_ctx(sandbox=True)`.

Честная оговорка: для stdio это не граница безопасности (клиент и сервер — один пользователь),
а защита от случайной записи мимо проекта. Тесты: `test_safe_path_blocks_escape`,
`test_check_paths_enforces_write_sandbox`.

### 1.5. «Подтверждение человеком» было формальным

**Было.** Достаточно любой непустой строки в `confirm.by`; проверка проходила со значением
`ai-agent`.

**Стало.** `check_approval()` отсекает машинные идентичности (`ai`, `agent`, `агент`, `bot`,
`gpt`, `llm`, `system`, `робот`, `api`, `cron` …), требует правдоподобное имя и роль.

Главное — **честность статуса**: подтверждение помечается `identity_verified: False` с
пояснением «идентичность не привязана к учётной записи: проверен только формат подписи».
В аудит пишется блок `approval_identity`. Это значит: код не делает вид, что доказал, кто
подтвердил.

Чего это не заменяет: настоящей привязки к учётной записи (IdP, SSO, одноразовый код).
См. п. 5.1 — осталось.

Тесты: `test_machine_or_empty_identity_is_rejected` (9 значений),
`test_human_identity_accepted_but_marked_unverified`,
`test_commit_with_machine_identity_is_blocked`.

### 1.6. Аудит-цепочка

**Было.** (а) При 8 потоках по 15 записей `verify()` выдавал «разрыв цепочки prev_hash»:
чтение хвоста и запись не атомарны. (б) Удаление последних двух записей `verify()` не
замечал, внешнего якоря не было.

**Стало.**

* **Запись под блокировкой.** Критическая секция «прочитать хвост → посчитать хэш →
  дописать» защищена мьютексом потока и `flock` на lock-файле журнала. Тест
  `test_audit_chain_survives_parallel_writes`: 8 потоков × 15 записей = 120, цепочка цела.
* **Якорь хвоста.** `audit anchor` пишет рядом с журналом `<файл>.head`: число записей и
  последний хэш, атомарно (запись в temp + rename). `audit-verify --anchor` сравнивает
  журнал с якорем и говорит прямо: «журнал короче якоря: записей 4, в якоре 6 — последние
  записи удалены». Тест `test_anchor_detects_truncated_tail`.
* В CI сквозной прогон теперь выполняет `audit anchor` + `audit-verify --anchor`.

Ограничение, которое надо назвать вслух: якорь лежит рядом с журналом, поэтому тот, кто
может переписать оба файла, обойдёт и его. Для защиты от владельца каталога нужен внешний
якорь (отдельный сервис/нотаризация хэша) — это п. 5.2.

## 2. Серьёзное — исправлено

### 2.1. В акты попадали открытые работы

**Было.** «Розетка неутопленного типа при открытой проводке» и «короба» попадали в АОСР:
деление шло по группам, а не по признаку «скрыто/открыто».

**Стало.** В матрице появилось правило `open_work_rule` и функция `is_open_work()` —
признак берётся только из прямых формулировок: «открытая прокладка/проводка/монтаж»,
«открыто по стенам», «по поверхности стен», «неутопленного типа». Такие позиции не попадают
в акты и уходят в `excluded` с причиной «открытые работы (прокладка/монтаж по поверхности):
акт на скрытые работы не оформляется».

Эффект на реальной смете 1166/Н: в актах было 19 позиций, стало 16 — ровно те три
(розетка и два выключателя неутопленного типа при открытой проводке). Тесты:
`test_open_work_detected`, `test_plan_acts_excludes_open_works`,
обновлённые `test_asbuilt_aros.py`.

### 2.2. Классификатор вне электрики был слабым

**Было** (синтетические сметы ревьюера): кровля 2 из 4, земля/фундамент 4 из 6,
ВК 1 из 4, слаботочка 2 из 5, отделка 2 из 5; радиаторы не распознавались.

**Стало.** Причин было две: (1) у видов работ не хватало сильных ключей, (2) ключ из
нескольких слов искался как одна строка, поэтому «бетонн подготовк» не находило
«бетонной подготовки».

* Добавлено **57 сильных ключей** в 7 видов работ: кровля (`кровел`, `рулонн кровл`,
  `утеплен покрыт`), бетон (`бетонн подготовк`, `подбетонк`, `монолитн плит`), ВК
  (`водопровод`, `полипропилен`, `унитаз`, `мойк`, `раковин`, `смесител`, `гидроиспытани`),
  слаботочка (`видеокамер`, `турникет`, `патч-панел`), пожарная сигнализация
  (`приемно-контрольн`, `пкп`, `извещател`, `оповещен`, `дымоудален`, `впв`), отделка
  (`линолеум`, `наливн пол`, `дверн блок`, `оконн блок`, `обои`, `гипсокартон`), ОВиК
  (`радиатор`, `конвектор`, `промывк систем`, `испытани систем отоплен`).
* Сопоставление многословных ключей теперь учитывает окончания в каждом слове.

Все 16 примеров из ревью распознаются: `test_classifier_recognises_review_examples`
(16 параметризованных случаев). Шифр расценки по-прежнему не читается как слово

Остаток по этому пункту честно: матрица покрывает 17 видов работ, и в ней нет отдельных
видов для «слаботочка: ПНР», «кровля: примыкания», «отопление: промывка и гидроиспытание»
как самостоятельных актов. Позиции распознаются и попадают в акт своего вида, но отдельного
акта под них пока нет — п. 5.3.

## 5. Что осталось — с причиной и оценкой

### 5.1. Привязка подтверждения к учётной записи (критично, ~1–2 дня)

Сейчас проверяется формат подписи и отсекаются машинные идентичности, но доказать, что
`Иванов И.И.` — это Иванов, код не может. Нужен один из вариантов: вход через корпоративный
IdP (OIDC/SAML) с токеном в подтверждении; одноразовый код на телефон/почту; подпись УКЭП.
Пока это не сделано, в аудите честно стоит `identity_verified: false` — и это надо сохранить,
а не «включить» формально.

### 5.2. Внешний якорь журнала (критично для доказательности, ~2 дня)

Якорь рядом с журналом защищает от случайного и «тихого» удаления хвоста, но не от того, кто
владеет каталогом. Варианты: отправка хвостового хэша по расписанию во внешнюю систему
(СЭД, почта, нотаризация), либо неизменяемое хранилище (WORM/S3 Object Lock).

### 5.3. Отдельные акты для «отопление», «слаботочка», «кровля» (серьёзно, ~1 день)

Позиции теперь распознаются, но группируются по общим группам вида работ. Нужны группы актов
«испытание и промывка систем отопления», «ПНР слаботочных систем», «примыкания и парапеты
кровли» с их протоколами.

### 5.4. `report.py` и покрытие CLI (умеренно, ~0,5 дня)

`report.py` — 0 %: тесты не вызывают его напрямую. CLI не виден в покрытии, потому что
тесты запускают его подпроцессом; лечится либо `coverage run -m pytest` с
`concurrency=subprocess`, либо переносом логики отчётов в тестируемые функции.

### 5.5. Нормативная база: ПУЭ 1.8.37/1.8.39 (серьёзно, зависит от источника)

В базе лежит фрагмент ПУЭ-7 (пп. 1.8.37, 1.8.39) обрезанный после п. 3.2; 1.8.39 не
подтверждён первоисточником. Правило проекта: **нормы не берутся по памяти и не
дописываются из головы** — нужен текст из официального источника (или ЭД), после чего
фрагмент заменится полным пунктом. До этого статус `verified_partial` остаётся честным.

### 5.6. Деньги в `Decimal` (умеренно, ~0,5 дня)

`reconcile.py` и `impact.py` считают в `float` с округлением до копеек. Для сумм актов
правильнее `Decimal`: сейчас расхождение в 1 копейку возможно на длинных рядах. Работы
затрагивают сверку, деньги и КС-2 — менять надо с пересчётом эталонных цифр в тестах.

### 5.7. Пересчёт единиц («100 м2» → «м2») (умеренно, ~0,5 дня)

Сейчас «100 м2» и «м2» — несовпадение единиц, а не конверсия. Нужен словарь кратных
единиц (100 м², 1000 м³, кг/т) с явным журналированием конверсии в аудите.

Ревью не покрывало: `parsers`, `matching`, `export`, `materials`, `procurement`, `prices`,

(xlsx-бомбы, гигантские ячейки); (4) `kr_pdf`/`takeoff`/`kr_schedules` — целостность цифр
(частично уже покрыто тестами).
