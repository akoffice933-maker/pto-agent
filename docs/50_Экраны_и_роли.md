# 50. Экраны и роли (этап 5)

Что это: серверный интерфейс учёта — FastAPI + Jinja2 + HTMX. Прораб подаёт требование
М-11 из браузера, снабженец проводит приход и первую ступень согласования, ПТО подписывает
вторую, руководитель — третью, бухгалтер проводит оплату, принимает предложенные проводки и
закрывает месяц. Права проверяются **на сервере** по файлу данных, а не в шаблоне.

## 1. Запуск

```bash
pip install -r requirements-pto.txt          # fastapi, uvicorn, jinja2, itsdangerous, multipart
python3 -m pto_agent web --root out --demo --host 0.0.0.0 --port 8000
# или
python3 -m pto_agent.web --root out --demo --port 8000
```

`--demo` собирает состояния контуров из `data/demo` теми же функциями, что и CLI:
склад (`stock.post_many`), проводки (`ledger.post_stock`), казначейство
(`treasury.add_request`). Ни одна цифра для экрана не рисуется отдельно.

Демо-логины (витрина ролей, не боевая аутентификация) печатаются на странице входа:

| логин | пароль | роль | что может |
|---|---|---|---|
| `prokhorov` | `demo-prokhorov` | прораб | склад (просмотр), требование М-11, заявка, акты |
| `snab` | `demo-snab` | снабженец | приход, заявка, ступень «снабжение» |
| `pto` | `demo-pto` | ПТО/сметчик | акты, ступень «ПТО», аудит |
| `buh` | `demo-buh` | бухгалтер | проводки, оплата, закрытие, отчёты |
| `dir` | `demo-dir` | руководитель | сводка, ступень «финдиректор» |
| `admin` | `demo-admin` | администратор | пользователи и матрица прав; проводок не касается |
| `agent` | `demo-agent` | ИИ-агент (сервис) | только чтение |

## 2. Матрица прав — файл данных, проверка на сервере

`data/reference/rbac.json` (схема `pto-agent/rbac@1`):

- `roles` — роль → список прав (`postings.post`, `closing.run`, `request.approve:ПТО`, …);
- `object_scope` — `own` (только свои объекты), `all`, `none`;
- `actions` — человекочитаемые названия прав;
- `rules` и `not_implemented` — то, что показано администратору на экране «Роли».

Проверка идёт в одном месте — `pto_agent/web/rbac.py:Matrix.can()`. Шаблон только прячет
кнопки: отказ всё равно приходит с сервера, кодом и причиной (403, `FORBIDDEN` /
`OBJECT_FORBIDDEN` / `AGENT_FORBIDDEN`).

Ступень согласования — часть права: `request.approve:снабжение`, `request.approve:ПТО`,
`request.approve:финдиректор`. Две проверки складываются: матрица отвечает на вопрос
«может ли эта роль подписывать эту ступень», казначейство — «чья сейчас очередь и не одно
ли это лицо» (`WRONG_STEP`, `SAME_PERSON`).

Область объектов: `object_scope` + `objects` в `users.json`. Требование на чужой объект
отвергается `OBJECT_FORBIDDEN`, а не «молча не показывается».

## 3. ИИ-агент не проводит документы — это ограничение в коде

Два уровня:

1. у роли `ИИ-агент` в матрице нет ни одного права на запись (`postings.post`,
   `postings.accept`, `closing.run`, `request.approve`, `request.pay`, `warehouse.issue`,
   `warehouse.receipt`, `request.create`);
2. каждый пишущий обработчик идёт через `_guard()`: сначала «это человек?» — сервисный актор
   получает `AGENT_FORBIDDEN`, потом «есть ли право?». Порядок намеренный: отказ виден как
   техническое ограничение, а не как отсутствие настройки.

Проверяется в `tests/test_web.py` (`test_agent_reads_but_does_not_post`,
`test_agent_cannot_close_month`) и в `scripts/check_web.py`.

## 4. Экраны

| путь | право | что делает |
|---|---|---|
| `/` | любое из прав роли | сводка: склад в деньгах, деньги казначейства и расхождение с 51, журнал, заявки, предложенные проводки, закрытые месяцы |
| `/warehouse` | `warehouse.view` | остатки по складам (HTMX-фильтр), последние документы, бланк М-11 |
| `/warehouse/issue` | `warehouse.issue` | форма требования М-11: объект, склад, до 5 строк; проведение через `stock.post_document` |
| `/warehouse/issue/{номер}.docx` | `warehouse.issue` | печатная форма М-11 по фактическим движениям (черновик, без подписи) |
| `/acts` | `act.view` | реестр КС-2 и признак «признан в проводках» |
| `/requests` | `request.view` | заявки, маршрут, подписи, кнопки своей ступени и оплаты |
| `/requests/new` | `request.create` | подача заявки; отказ без документа-основания (`NO_BASIS`) |
| `/postings` | `postings.view` | ОСВ за период, забалансовые счета, проводки, предложения |
| `/closing` | `closing.view` / `closing.run` | проба и закрытие месяца шагами (`closing.close_month`) |
| `/audit` | `audit.view` | хэш-цепочка действий с ролью и IP + проверка целостности |
| `/roles` | `admin.rbac` | матрица, пользователи, правила, «не сделано» |

Экраны не считают: остатки — `stock.balances`, ОСВ — `ledger.trial_balance`, закрытие —
`closing.close_month`, бланк — `forms.build_stock_form`. Если цифра на экране отличается от
CLI, значит они читают разные состояния, а не «по-разному считают».

## 5. Аудит

Каждое действие и **каждый отказ** пишутся в ту же хэш-цепочку (`pto_agent/audit.py`):
кто (логин и ФИО), роль, что, объект, IP (`X-Forwarded-For` или адрес сокета), путь,
результат. Проверка целостности — на экране `/audit` и в `AuditLog.verify()`.

## 6. Что не сделано (честно)

- боевая аутентификация: AD/LDAP, 2FA — нет; пароли в файле, PBKDF2-SHA256;
- подпись УКЭП из браузера — этап 7; печатные формы остаются черновиками;
- акт КС-2 не проводится из браузера: признание выручки требует подписанта, экран этого
  не делает намеренно;
- разграничение по сумме внутри роли — нет, сумму закрывает маршрут согласования;
- сессии живут в подписанной куке: без `--secret` они сбрасываются при перезапуске сервера;
- экраны не покрывают зарплату (этап 6) и налоги/ЭДО (этап 7).

## 7. Проверки

```bash
python3 scripts/check_web.py     # сквозной сценарий: требование → маршрут → оплата → закрытие → аудит
python3 -m pytest tests/test_web.py -q
```

`check_web.py` входит в CI рядом с `check_ledger.py` и запускается до `pytest`.
