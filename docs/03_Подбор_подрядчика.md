# 1. Главный вывод

Проверено 19 организаций и профилей, включая всех авторов репозиториев из раздела 14 ТЗ.

**Ни одна команда на GitHub не закрывает проект целиком.** Лучший результат по интегральной оценке — 3,25 из 5, и он у одиночного разработчика с сильной доменной экспертизой, а не у студии. Причина не в слабости рынка, а в структуре задачи: ПТО требует одновременно четырёх компетенций, которые на рынке почти не встречаются в одной команде:

| Компетенция | Где на рынке | Дефицит |
|---|---|---|
| Домен ПТО (КС-2, АОСР, комплектность, СП) | одиночные инженеры и авторы пет-проектов | нет мощности под MVP |
| RAG по нормативам + оценка качества | российские ИИ-интеграторы | нет домена |
| CAD/DWG headless + оформление по ГОСТ | международные AEC-разработчики | нет РФ-контура и 1С |
| On-prem, 152-ФЗ/187-ФЗ, 1С/ЭДО | системные интеграторы и вендоры | нет ИИ-инженерии в публичном виде |

**Рекомендация: гибридная модель** — российский интегратор как лид (RAG, on-prem, 1С/ЭДО), AEC-специалист на CAD-модуль, доменный эксперт ПТО на правила и приёмку, заказчик как владелец данных и эталонной выборки. Подробно — раздел 8.

Второй вывод: **публичный GitHub — плохой фильтр для российских интеграторов.** Крупные студии и интеграторы (ЛАНИТ, КРОК, Инфосистемы Джет, Arinit, LLM Studio) либо не ведут публичный код, либо ведут его без связи с коммерческими проектами. Поэтому отбор идёт в два контура: GitHub + референсы.

# 7. Что делать с авторами чужих репозиториев

Отдельно про `construction-ai-core`, `moge-document-expertise-ai`, `AutoGAD` и другие проекты из раздела 14 ТЗ: **у них нельзя просто взять код**, но можно заказать работу их авторам.

| Вариант | Как оформить | Риск |
|---|---|---|
| Заказать консультацию автора | договор возмездного оказания услуг, NDA, оплата по часам | знания без гарантий, автор может быть недоступен |
| Купить права на код | договор об отчуждении исключительного права, проверка авторства | неясная история кода, отсутствие тестов |
| Взять как референс | изучение архитектуры, самостоятельная реализация | повторим чужие ошибки, но без юридических рисков |
| Использовать как есть (MIT/Apache) | включение с сохранением уведомлений, SBOM | допустимо; AGPL и «без лицензии» — нельзя |

# 8. Рекомендуемая конфигурация

**Гибрид с внутренним владельцем продукта.** Состав на MVP:

| Роль | Кто | Загрузка | Зона ответственности |
|---|---|---|---|
| Владелец продукта | заказчик (нач. ПТО / директор по цифровизации) | 0,5 FTE | приоритеты, эталонная выборка, приёмка, споры |
| Лид-интегратор | RU-студия (Byndyusoft / Arinit / аналог) | команда 3–4 чел. | RAG, оркестрация, on-prem, 1С/ЭДО, CI/CD |
| AEC/CAD-подрядчик | Intent Solutions / Deuz AI / локальный CAD-разработчик | 0,3–0,5 FTE или фикс-скоуп | CAD-модуль, DWG/DXF, оформление |
| Доменный эксперт | А. Гребешок или свой ведущий инженер ПТО | 0,3 FTE | правила КС-2/АОСР, шаблоны, разметка, приёмка |
| ИБ-контур | ИТ-служба заказчика | по этапам | классификация данных, тесты, аудит |

Ориентир бюджета MVP в такой конфигурации — **10–16 млн ₽** и 5–7 месяцев; при этом знание остаётся внутри компании, а не уходит вендору.

# 9. Как отбирать: три шага

**Шаг 1. Кабинетная проверка (1 неделя, бесплатно).** Прогнать 5–7 кандидатов по чек-листу «Проверка GitHub» и 25 вопросам RFP (см. xlsx). Отсечь тех, кто не отвечает на вопросы про цитаты, конвертацию DWG и приёмку по метрикам.

**Шаг 2. Платный пилот на 2 недели (200–400 тыс. ₽).** Одна задача: **сформировать черновик КС-2 по нашим 5 реальным документам с таблицей расхождений**. Что смотрим: работает ли на наших данных, сколько позиций верно, как ведёт себя на плохом скане, что показывает при неуверенности. Пилот — единственный надёжный фильтр.

**Шаг 3. Контракт.** Фиксированный объём MVP, оплата по этапам, приёмка по golden set с порогами из ТЗ (recall ошибок ≥ 0,95, точность цитат ≥ 99 %, ноль ошибок арифметики).

# 10. Что обязательно требовать в договоре

| Требование | Формулировка |
|---|---|
| Права на результат | исключительные права на код, модели-адаптеры, промпты и шаблоны переходят заказчику |
| Данные | данные заказчика не используются для обучения сторонних моделей; после проекта удаляются из контуров подрядчика |
| SBOM | перечень open-source компонентов с лицензиями; AGPL и компоненты без лицензии запрещены |
| Приёмка | по метрикам на эталонной выборке заказчика, а не по демонстрации |
| Передача | документация, тесты, инструкции, доступ к репозиторию заказчика; bus factor ≥ 2 |
| On-prem | поставка и развёртывание в контуре заказчика без доступа в интернет |
| Ответственность | штраф за утечку данных и за использование запрещённых лицензий |

# 11. Красные флаги

- «Мы сделаем на GPT через API» — без обсуждения контура и 152-ФЗ.
- Нет ответа на вопрос про цитаты норм или ответ «модель не ошибается».
- Демонстрация на чужих/синтетических документах вместо ваших.
- Отказ от пилота «потому что и так понятно».
- Нет тестов и CI в публичных репозиториях, но есть презентация на 30 слайдов.
- Использование AGPL-компонентов или кода без лицензии.
- Приёмка «по акту осмотра», без метрик.
- Один человек на все роли при заявленной команде 10 специалистов.
