# Распознавание сканов redline локальной VL-моделью

**Версия:** 0.1.0 · **Дата:** 03.11.2026 · **Статус:** рабочий модуль; прогон на демо-скане пройден в двух режимах (VL-модель / офлайн-CV), боевая модель в контуре заказчика ещё не подключалась

Модуль закрывает то звено, которое раньше держалось на человеке: инженер присылает скан листа
с рукописными пометками (redline), а агент ПТО сам находит пометки, читает их, переводит в
координаты чертежа и превращает в типизированные операции. Модуль встроен в тот же конвейер,
что и CAD-модуль из документа 05: `операции → validate_operations → dry_run → commit с подписью`.

## 2. Как это работает

```
фото/скан листа (PNG/JPG)
   │
   ├─ 1. калибровка ────── рамка листа на скане ↔ габариты DXF → ед/px, сдвиг
   │                        (или ручные опорные точки, или готовая калибровка из JSON)
   ├─ 2. нарезка ───────── тайлы 1600 px с перекрытием 10 % — модель не теряет мелкий текст
   ├─ 3. распознавание ─── VL-модель по OpenAI-совместимому API (vLLM) ИЛИ офлайн-CV
   │                        ответ — строгий JSON: type / bbox 0..1 / text / confidence
   ├─ 4. проверки ──────── схема ответа, координаты в листе, размер bbox,
   │                        ЧЕРНИЛА ПОД BBOX (анти-галлюцинация), склейка дублей
   ├─ 5. тексты инженера ─ ручной ввод для нечитаемых пометок (привязка по геометрии)
   └─ 6. план ──────────── пометка → операция белого списка + source.ref + reason
                            либо конфликт с КС-2/журналом → вопрос человеку
```

Промпт и схема ответа версионированы (`prompt.py`: id `redline_scan`, версия `1.0`), версия
пишется в каждый вызов модели — при смене модели или промпта старые прогоны отличимы в аудите.

### Почему ответ модели не принимается на веру

1. **Схема.** Неизвестный тип пометки, перевёрнутый или нулевой bbox, координаты за пределами
   листа, отсутствие `confidence` — отказ с кодом причины (`TYPE`, `BBOX_INVERTED`,
   `BBOX_OUT_OF_RANGE`, `CONFIDENCE_MISSING`).
2. **Чернила под bbox.** Под каждым предложенным bbox считается доля цветных чернил по самому
   скану; если меньше 0,4 % — `NO_INK_IN_BBOX`, пометка отбрасывается. Это ловит главный класс
   ошибок VL-моделей: «уверенно увидела» обводку там, где ничего нет.
3. **Порог уверенности.** `confidence < 0,7` или пустой текст — не операция, а вопрос человеку
   (`needs_human_decision`), даже если модель уверена в типе.
4. **Сверка с ПТО.** Пометка сверяется с журналом работ и КС-2: «согласовано» на позиции с
   критичным расхождением и объём в пометке, расходящийся с актом, — конфликт, а не операция.

## 3. Два режима распознавания

| | `--engine vlm` (боевой) | `--engine offline` (без модели) |
|---|---|---|
| Что делает | локальная Qwen2.5-VL (`local-qwen-vl-32b`) по API vLLM | вычитание эталонной растеризации чертежа (DXF → PNG) из скана, анализ остатка |
| Что читает | текст пометки (рукописный) | только геометрию: обводку, подчёркивание, стрелку |
| Что нужно | GPU-контур + доступ по сети | DXF-исходник + калибровка |
| Стоимость | 0 ₽ (свой сервер) или цена провайдера; пишется в `out/cad/llm_calls.jsonl` | 0 ₽ |
| Роль | основной путь | проверка «сошлось ли количество пометок», работа без GPU |

Третий режим — `mock`: локальная заглушка отдаёт эталонные пометки по HTTP в том же формате,
что и настоящая модель. Нужен, чтобы прогонять весь конвейер (тайлы → HTTP → проверки →
операции) без внутреннего контура. Заглушка всегда сообщает о себе предупреждением
`MOCK_PROVIDER`, чтобы её ответ нельзя было принять за работу модели.

Отдельно зафиксировано: **эвристика «цветные чернила» как основной метод отброшена.** На первом
прогоне она дала 9 пометок вместо 5 — жёлтые маркеры плиты и квадраты-точки на чертеже
попадали под определение «цветные чернила», а обводка и подпись сливались или распадались.
Рабочим методом без модели стало вычитание эталонной графики (`reference_diff`), эвристика
осталась черновым fallback, когда DXF-исходника нет.

## 4. Запуск

```bash
# 0. демо-скан (шум, поворот, поля бумаги) + эталонные пометки
python3 scripts/make_demo_redline.py

# 1. только распознавание (ничего не меняет)
python3 -m pto_agent cad scan --scan drawings/redline_scan.png \
        --file drawings/korpus2_plan_v1.dxf --engine vlm --json out/cad/scan.json

# 2. распознавание без модели, тексты вводит инженер
python3 -m pto_agent cad scan --scan drawings/redline_scan.png \
        --file drawings/korpus2_plan_v1.dxf --engine offline --texts data/demo/redline_texts.json

# 3. полный путь: скан → операции → проверка (ничего не пишет)
python3 -m pto_agent cad redline-from-scan --scan drawings/redline_scan.png \
        --file drawings/korpus2_plan_v1.dxf --engine vlm --summary out/summary.json \
        --mode plan_only --out out/cad/scan_plan.json

# 4. применение: сначала dry_run, потом commit с ФИО подтвердившего
python3 -m pto_agent cad redline-from-scan --scan drawings/redline_scan.png \
        --file drawings/korpus2_plan_v1.dxf --engine offline --texts data/demo/redline_texts.json \
        --mode commit --confirm-by "Иванов И.И." --out-dxf out/cad/korpus2_plan_v1_scan_markup.dxf

# 5. MCP (для внешнего агента): те же шаги по протоколу
python3 -m pto_agent.cad.mcp_server --transport http --port 8765
```

`commit` без `--confirm-by` отклоняется кодом `NO_HUMAN_CONFIRMATION`, код возврата 2.
Демонстрационно: `cad redline-from-scan` без подтверждения → отказ, с подтверждением →
31 → 35 объектов, запись в `out/cad/audit.jsonl` и `out/cad/history.jsonl`.

## 5. Результат на демо-скане

### 5.1 Что на скане и что нашлось

| Пометка | Тип на скане | Текст (рукописный) | Что сделал модуль |
|---|---|---|---|
| m1 | стрелка | — (без текста) | вопрос человеку: «текст пометки не распознан» |
| m2 | обводка | «Ду50 → Ду100 по АОСР-146» | `ADD_CLOUD` на блок `10A` (ФЕР 16-02-003-01) + `ADD_TEXT` с обозначениями Ду50/Ду100 |
| m3 | обводка | «СОГЛАСОВАНО» | **конфликт `CONFLICT_APPROVAL`**: по ФЕР 06-01-001-01 у ПТО критичное расхождение (VOLUME_OVER_ESTIMATE) → решение человеку |
| m4 | подчёркивание | «1300 м3 — принять по факту» | **конфликт `CONFLICT_QUANTITY`**: в пометке 1300 м3, в акте 1240 м3 (+4,8 %) → пересчёт или подтверждение |
| m5 | перечёркивание | «отмостку исключить» | `ADD_CLOUD` на позицию отмостки (без шифра расценки — так и написано в `reason`) |

Точность bbox относительно эталона: режим `vlm` — IoU = 1,00 по всем пяти; офлайн-детектор
находит те же 5 пометок, но его bbox шире, потому что включает рукописный текст рядом
(IoU 0,07–0,71, попадание эталона в найденный bbox — от 0,45 до 1,0). Для плана операций этого
достаточно: адресат определяется по попаданию рамки в позицию или по близости ≤ 3 м.
Для точной геометрии (выпуск облаков «в размер») нужна модель — офлайн-режим честно
годится для контроля количества и для работы без GPU.

### 5.2 План операций (фрагмент)

```json
{"op_id": "op-001", "type": "ADD_CLOUD",
 "params": {"entity_handle": "10A", "margin": 2500.0, "layer": "ПОМЕТКИ"},
 "reason": "пометка на скане (circle) относится к позиции ФЕР 16-02-003-01, привязка по ближайшей позиции",
 "source": {"type": "redline_scan", "ref": "m2", "confidence": 0.88, "image": "drawings/redline_scan.png"},
 "requires_confirmation": true}
```

У каждой операции есть `source.ref` (номер пометки на скане) и `reason` (почему именно эта
позиция). Привязка помечена способом: `in_box` — центр позиции внутри пометки, `nearest` —
по близости, `by_quantity` — по объёму из пометки (и тогда в `reason` прямо написано
«проверить глазами»), `text_entity` — надпись без шифра расценки.

### 5.3 Что получилось на листе

`out/cad/scan_markup_preview.png` — два облака и два пояснения на слое `ПОМЕТКИ`, рядом с
позициями Ду50 и отмостки. Печатная графика, штамп и защищённые слои не затронуты
(`validate_operations`: 0 блокирующих).

## 6. MCP

Добавлены два инструмента (всего 12, `/health` подтверждает):

| Инструмент | Вход | Выход |
|---|---|---|
| `scan_redline_image` | `scan_path`, `file_path`, `engine`, `texts_path`, `truth_path`, `calibration`, `provider` | пометки с координатами модели, `stats`, `rejected`, `warnings`; ничего не меняет |
| `plan_from_scan_redline` | те же + `summary_path`, `markup_layer`, `template_path` | операции, конфликты, вопросы человеку + `validation` чертежа по шаблону |

Дальше внешний агент работает обычным путём: `validate_operations` → `apply_operations`
(`dry_run`, затем `commit` с объектом `confirm {by, role, comment}`).

## 7. Что проверено тестами (24)

| Группа | Что утверждается |
|---|---|
| Схема | отбраковка неизвестного типа, перевёрнутого/нулевого bbox, координат вне листа, отсутствия confidence; разбор объёмов и признаков согласования |
| Калибровка | авто-калибровка по рамке даёт одинаковый масштаб по X и Y (расхождение < 1 %); без двух опорных точек — ошибка |
| Провайдер | при недоступном внутреннем контуре — `ProviderUnavailable`, а не зависание и не тихая подмена модели |
| Mock-сервер | формат ответа как у OpenAI `/v1/chat/completions`, координаты относительны фрагмента и возвращаются в пиксели листа |
| Распознавание | 5 из 5 пометок, IoU = 1,0 к эталону, тексты совпадают; каждый вызов записан в `llm_calls.jsonl` с версией промпта и хэшем картинки |
| Анти-галлюцинация | выдуманный bbox в пустом месте листа → `NO_INK_IN_BBOX` и пометка не попадает в план |
| Тексты инженера | привязка по геометрии (bbox), а не по номеру: у офлайн-детектора своя нумерация; после подстановки `engine = human`, `confidence ≥ 0,95` |
| План | совпадение плана в обоих режимах (4 операции, 2 конфликта, 3 вопроса); у каждой операции есть `source.ref` и `reason`; операции проходят `validate_operations` без блокирующих |
| Конфликты | «согласовано» против критичного расхождения ПТО; 1300 м3 против 1240 м3 в акте |
| MCP | 12 инструментов; `plan_from_scan_redline` возвращает план + валидацию чертежа |

## 8. Честные ограничения

1. **Боевая модель не подключена из песочницы.** `local-qwen-vl-32b` живёт во внутреннем
   контуре (`10.20.0.12:8000`), из песочницы недоступен. Проверка шла на заглушке с тем же
   протоколом и на офлайн-CV. Что нужно сделать в контуре: поднять vLLM с Qwen2.5-VL, указать
   `PTO_VL_BASE_URL`, прогнать `cad scan --engine vlm` на 15–20 реальных сканах и свести ошибки
   в таблицу «пометка → что прочитала модель → что было на самом деле».
2. **Скан демонстрационный.** Синтетический лист: шум, поворот, поля, рукописный шрифт.
   Реальные сканы бывают темнее, с бликами, с пометками поверх плотной графики.
3. **Тип пометки приблизителен.** Офлайн-детектор различает обводку/подчёркивание/стрелку
   по пропорциям и плотности штриха; перечёркивание иногда читает как обводку. Тип влияет
   только на `reason`, не на адресата; в плане он всегда указан, чтобы инженер видел основание.
4. **Поворот скана.** Компенсируется калибровкой по рамке, но при съёмке «на телефон» с
   перспективой нужны 4 опорные точки (`Calibration.from_anchors`), а не авто-режим.
5. **DWG** — по-прежнему только через конвертацию в DXF (как и в документе 05).
6. **Рукописный текст без модели не читается.** Это принципиально: офлайн-режим считает
   пометки и их геометрию, текст вводит человек (`--texts`) — тогда пометки становятся
   операциями без участия модели.

## 9. Что дальше

1. Прогон на реальных сканах в контуре заказчика — таблица ошибок по 15–20 листам.
2. Перспективная калибровка по 4 опорным точкам (съёмка на телефон) и проверка на наклоне.
3. Пакетная обработка выпуска: 30–50 листов за сеанс, сводка пометок одним отчётом.
4. Обратная связь: правки инженера после `dry_run` сохраняются как обучающие пары
   «скан → правильная пометка» для подстройки промпта.
5. Перенос рукописного текста в атрибуты объектов (не только в пояснение), когда появится
   корпоративный регламент на такие правки.
