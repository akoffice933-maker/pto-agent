# Портфель актов: деньги под риском по объекту и по месяцам

**Версия:** 0.5.0 · **Дата:** 03.11.2026 · **Статус:** работает на демо-данных MVP

Предыдущий шаг отвечал на вопрос «сколько стоит спор по одному акту». Руководителю нужен
объект: **сколько всего предъявлено, какая доля этого проверена и сколько денег висит под
вопросом по месяцам**. Этот модуль собирает реестр актов объекта, считает деньги по каждому
акту теми же правилами и сводит всё в одну таблицу — с честным ответом там, где проверки
не было. После ретро-проверки прошлых актов непроверенных актов на объекте не осталось.

## 2. Почему одного акта мало

| Вопрос | Ответ одного акта | Ответ портфеля |
|---|---|---|
| Сколько денег под риском | 1 850 000 ₽ | 2 091 000 ₽ по трём актам |
| Какая часть предъявленного проверена | не видно | 100 % после ретро-проверки (было 88,54 %) |
| Что было в прошлом месяце | не видно | сентябрь: 4 416 000 ₽, под риском 241 000 ₽ |
| Где узкое место | не видно | сначала это было ретро (4,4 млн без проверки), теперь — подпись «согласовано» и завышение по плите в октябре |

## 3. Правила расчёта

1. **Непроверенный акт — это «не оценено», а не «0 ₽».** Ноль в графе «под риском» читается
   как «там всё чисто». Пока ретро-выпуска не было, два акта так и показывались — с причиной
   и суммой, а не с нулём.
2. **Сумма по объекту = сумма по актам.** Каждая цифра на странице складывается из строк
   таблицы актов.
3. **Одна позиция в двух актах — это два спора** (разные периоды и предъявления), их суммы
   складываются. Повторы одной пометки внутри акта по-прежнему считаются один раз.
4. **Сверка идёт с количествами того акта, который проверяется.** Для ретро-актов собирается
   отдельная сводка ПТО периода: иначе пометка «210 м³» сравнивалась бы с октябрьским
   журналом (1 240 м³) и конфликта не было бы вообще.
5. **Направление спора сохраняется.** По акту №37 пометка «180 м» при акте 200 м — это
   недополученные 24 800 ₽, отдельная строка, а не «минус» в завышении.
6. **Доля считается от проверенного, покрытие — отдельно.** 5,43 % — от 38,5 млн проверенных
   актов; покрытие 100 % — какая часть предъявленного проверена.

## 4. Ретро-проверка актов №35 и №37

Первый прогон портфеля показал главное: самое дорогое место — не текущий выпуск, а два
уже подписанных акта на 4 416 000 ₽, которые никто не проверял. Поэтому для них собран
ретро-выпуск:

| Акт | Что нашли пометки | Деньги | Направление |
|---|---|---|---|
| КС-2 №35 (плита) | «210 м³ — принято по факту» против 200 м³ в акте | 185 000 ₽ | завышение |
| КС-2 №35 (гидроизоляция) | «640 м² — принять по факту» против 600 м² | 31 200 ₽ | завышение |
| КС-2 №37 (водопровод) | «180 м — факт» против 200 м в акте | 24 800 ₽ | **недополучено** |
| **Итого ретро** | 15 листов, 15 конфликтов | **241 000 ₽** | 216 200 / 24 800 |

Что это меняет: покрытие выросло с 88,54 % до 100 %, под риском — с 1 850 000 до 2 091 000 ₽,
и впервые появилась сумма недополучения: по водопроводу подрядчик предъявил меньше, чем
выполнил, — деньги, которые объект не получит без отдельного разбора.

## 6. Сведение с графиком финансирования

На дашборде руководителя рядом с планом/фактом освоения стоит блок «По месяцам: сколько
предъявлено и сколько под вопросом»:

- **предъявлено** (сумма актов месяца) — то, что уже в актах;
- **под риском** — часть предъявленного, которую заказчик вправе не принять;
- **уверенно к поступлению** ≈ предъявлено − под риском: сентябрь 4 175 000 ₽, октябрь
  32 256 600 ₽.

Если по какому-то месяцу акт не проверялся, «под риском» не подставляется нулём — строка
говорит «не оценено», и это отдельный пункт в списке решений: сначала проверить, потом
планировать.

## 7. Как запустить

```bash
# 1. реестр актов объекта (суммы — из актов, цены — из сметы)
python3 scripts/make_demo_acts.py            # → data/demo/acts/acts.json

# 2. ретро-выпуск по прошлым актам (сканы + сводка ПТО периода акта)
python3 scripts/make_demo_retro.py
python3 -m pto_agent cad scan-batch --manifest data/demo/retro/manifest_ks35.json \
        --engine vlm --summary out/acts/summary_ks35.json --out out/cad/batch_ks35
python3 -m pto_agent cad scan-batch --manifest data/demo/retro/manifest_ks37.json \
        --engine vlm --summary out/acts/summary_ks37.json --out out/cad/batch_ks37
python3 scripts/make_demo_acts.py            # реестр подхватит новые выпуски

# 3. портфель: все акты + месяцы + деньги под риском
python3 -m pto_agent cad impact --acts data/demo/acts/acts.json \
        --summary out/summary.json --out out/cad/portfolio

# 4. страница руководителя (блок «Деньги под риском» подтянется сам)
python3 docs/build_dashboard.py
```

`assess_release_impact` остаётся одним MCP-инструментом (их по-прежнему 14): с `batch_path`
он считает один выпуск, с `acts_path` — портфель актов.

`portfolio.xlsx`: «Портфель — итог» · «Акты» · «Месяцы» · «Позиции по актам» · «Расчёт по
актам» · «Не проверено» · «Не оценено» · «Методика».

## 9. Честные ограничения

1. **Ретро-сканы демонстрационные**, сводка периода акта собирается скриптом из
   `acts_previous.xlsx` и сметы. На реальном объекте источник — журнал работ и КС-2 того
   месяца из 1С; правило сверки от этого не меняется.
2. **Сверка по количествам ловит только превышение сметы.** Она не видит завышение внутри
   сметного объёма — для этого нужен распознанный выпуск.
3. **Суммы — по сметным ценам без выделения НДС.** При защите бюджета это указывается
   в подписи к таблице.
4. **Один объект — один реестр.** Разные объекты не складываются: у них разные акты, заказчики
   и графики.
5. **Ретро не восстановит закрытые акты.** Проверка показывает, где деньги, но подписанный
   акт остаётся подписанным: дальше — претензионная работа и правки в следующих КС-2.

## 10. Что дальше

1. **Прогноз исхода спора**: вероятность принятия и ожидаемая сумма по истории похожих
   споров, чтобы «под риском» превратилось в «ожидаемо к поступлению».
2. **Поправки в КС-2 из конфликтов**: какие строки и на сколько уменьшить, с подписью инженера.
3. **Интеграция с 1С**: реестр актов, оплаты и журналы — из системы, а не из файла.
4. **Автоматический ретро-прогон**: как только появляется акт без проверки — выпуск
   распознаётся по расписанию, а не по запросу.
