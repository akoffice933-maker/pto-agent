# 18. Прозрачность, реальная стадия и управленческая отчётность

## 18.1 Принцип

Руководитель должен получать **не отчёт о работе системы, а состояние объекта и проекта**: где мы находимся, сколько осталось, что уже получено, что мешает и кто отвечает. При этом любая цифра на экране обязана раскрываться до документа-источника в один клик.

Формулировка требования: **«одна страница — вся правда, каждая цифра — с адресом источника»**.

## 18.2 Требования к прозрачности действий

| ID | Требование |
|---|---|
| FR-TR-01 | Каждое действие агента и человека записывается в неизменяемый журнал: время, кто (пользователь или агент), действие, объект, основание (документ/лист/строка), модель и версия промпта, хэш артефакта |
| FR-TR-02 | Журнал append-only с хэш-цепочкой; изменение и удаление записей технически невозможны (триггер в БД) |
| FR-TR-03 | Прослеживаемость «цифра → расчёт → документ»: у каждой строки отчёта есть `trace_ref` на задачу и на источники |
| FR-TR-04 | Каждое действие, формирующее документ, порождает версию; предыдущая версия сохраняется и доступна для сравнения |
| FR-TR-05 | Разделение «выполнено» и «закрыто» на всех уровнях: физический факт (по журналам) и юридический факт (подписанный акт) показываются разными цифрами |
| FR-TR-06 | Все заблокированные действия видны явно: отказ `cite_verify`, непройденная валидация, отказ в подтверждении — с причиной |
| FR-TR-07 | История по объекту доступна за любой период (снимки состояния), а не только «на сейчас» |
| FR-TR-08 | Экспорт журнала и любой выборки — в XLSX/PDF, с сохранением `payload_hash` (что именно видел руководитель) |
| FR-TR-09 | Доступ к журналу — только чтение для аудитора и ИБ; администратор не может отключить журналирование |
| FR-TR-10 | Уведомления о критичных изменениях (расхождение, блокер комплектности, просроченный сертификат) — не позднее 5 минут после обнаружения |

## 18.3 Требования к отображению стадии («где мы сейчас»)

| ID | Требование |
|---|---|
| FR-ST-01 | Для каждой стадии проекта: план (даты), факт (даты), прогресс в %, статус (планово / в работе / риск / завершено) |
| FR-ST-02 | Обязательное текстовое поле «что реально сделано» — формулируется проверяемо, с цифрами и ссылками, без общих слов |
| FR-ST-03 | Обязательное поле «следующий шаг» и ответственный |
| FR-ST-04 | Контрольные точки стадии с измеримым критерием и статусом прохождения (пройдено / не пройдено / отложено) |
| FR-ST-05 | Отклонение от плана в днях рассчитывается автоматически, а не вводится вручную |
| FR-ST-06 | Прогресс не может быть «самооценкой»: учитываются только подтверждённые артефакты (пройденные тесты, размеченные документы, подписанные акты) |
| FR-ST-07 | При статусе «риск» требуется указать причину и меру; без этого стадия не может быть переведена в «завершено» |

## 18.4 Требования к остаточным объёмам («сколько осталось»)

**Расчётная формула (обязательная, единая для всей системы):**

```
Остаток = Объём по смете − Объём, закрытый подписанными КС-2 − Объём, выполненных по журналам, но не закрытый актом
```

| ID | Требование |
|---|---|
| FR-RM-01 | Остаток считается в натуральных единицах и в рублях, по каждому виду работ, захватке и подрядчику |
| FR-RM-02 | Работы, выполненные без подтверждающих документов, **не списываются** в остаток: они показываются отдельной колонкой «выполнено, не закрыто» |
| FR-RM-03 | Дополнительно показывается «готово к предъявлению» — деньги, заблокированные не работами, а документами |
| FR-RM-04 | Расхождение суммы остатков по видам работ и итога по объекту — 0 (проверяется автотестом) |
| FR-RM-05 | Снимок остатков формируется ежедневно; история доступна для сравнения периодов («остаток уменьшился на X за неделю — соответствует ли темпу?») |
| FR-RM-06 | Изменение остатка возможно только двумя путями: подтверждённый акт или подтверждённая запись журнала; ручная корректировка — с причиной и подписью |
| FR-RM-07 | Для каждой строки остатка: единица измерения, цена, источник сметы, ссылка на журнал/акт |
| FR-RM-08 | Остатки выгружаются в XLSX в структуре, пригодной для сверки со сметчиком и 1С |

## 18.5 Требования к отчёту руководителю

| ID | Требование |
|---|---|
| FR-RP-01 | Один экран/документ содержит: KPI, стадии проекта, остатки, деньги, качество и стоимость ИИ, последние действия, критичные расхождения |
| FR-RP-02 | Форматы: интерактивный HTML (портал), PDF (для совещаний), XLSX (для расчётов) |
| FR-RP-03 | Расписание: ежедневный утренний срез (07:00), недельный отчёт, срез по запросу; адресаты настраиваются |
| FR-RP-04 | Отчёт всегда датирован и версионирован; хранится `payload_hash` — доказательство того, что видел руководитель |
| FR-RP-05 | Блок «Требует решения» содержит: критичность, суть, привязку к виду работ и сумму влияния, кнопку перехода к карточке решения |
| FR-RP-06 | К отчёту прикладывается методика расчёта — чтобы цифры можно было оспорить и проверить |
| FR-RP-07 | Демонстрационные/тестовые данные маркируются на каждой странице (защита от использования демо-цифр в решениях) |
| FR-RP-08 | Отчёт не может быть «лучше» данных: если источник не загружен, показывается «нет данных», а не ноль |

## 18.6 Метрики и SLO прозрачности

| Метрика | Цель |
|---|---|
| Задержка от события до отражения в отчёте | ≤ 5 минут |
| Доля цифр отчёта с рабочим `trace_ref` | 100 % |
| Расхождение отчёта и первичных данных при выборочной сверке | 0 (проверка 10 цифр ежемесячно) |
| Доля действий, записанных в журнал | 100 % |
| Время на ответ на вопрос «откуда эта цифра» | ≤ 2 клика / ≤ 30 секунд |

## 18.7 Приёмочные критерии раздела 18

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-TR-01 | Любая цифра отчёта раскрывается до источника: смета (лист/строка), журнал, акт | Ручная проверка выборки 10 цифр комиссией |
| AC-TR-02 | Попытка изменить или удалить запись журнала возвращает ошибку БД | Автотест на триггере |
| AC-TR-03 | Остатки по видам работ сходятся с итогом по объекту до рубля | Автотест + сверка со сметчиком |
| AC-TR-04 | Отчёт формируется за ≤ 20 секунд, PDF выгружается без потери данных | Хронометраж |
| AC-TR-05 | «Выполнено» и «закрыто» различаются во всех блоках, включая графики | Экспертная проверка |
| AC-TR-06 | Стадия не может быть завершена без пройденных контрольных точек и заполненного факта | Автотест бизнес-правила |
| AC-TR-07 | Отчёт за прошлую дату воспроизводится из снимков и совпадает с сохранённым `payload_hash` | Тест воспроизводимости |

# 19. Подключение ИИ-моделей по API

## 19.1 Требование

Модель — сменный компонент. Приложение обращается к единому **LLM-шлюзу** с OpenAI-совместимым интерфейсом; конкретная модель определяется конфигурацией, а не кодом.

| ID | Требование |
|---|---|
| FR-LLM-01 | Шлюз поддерживает: локальные (vLLM/Ollama), РФ-облачные (GigaChat, YandexGPT) и любые OpenAI-совместимые API |
| FR-LLM-02 | Подключение новой модели — правка конфигурации + прогон приёмки, без выпуска новой версии приложения |
| FR-LLM-03 | Каждый вызов логируется: провайдер, модель, версия промпта, класс данных, токены, стоимость, задержка, результат валидации |
| FR-LLM-04 | Маршрутизация по классу данных: данные классов «коммерческая тайна» и «персональные» обрабатываются только в контуре заказчика |
| FR-LLM-05 | Данные класса «внешние API» физически не отправляются: блокировка на уровне шлюза и на уровне БД (триггер) |
| FR-LLM-06 | Бюджетные лимиты: месячный, дневной на пользователя, на задачу; при достижении порога — деградация на локальные модели, при 100 % — остановка внешних вызовов |
| FR-LLM-07 | Fallback-цепочка при таймауте, 429, 5xx, ошибке парсинга JSON; после исчерпания — эскалация человеку, а не имитация результата |
| FR-LLM-08 | Кэширование идемпотентных шагов (классификация, поиск норм) с TTL и областью действия |
| FR-LLM-09 | Ключи API — только в Vault/секретах, не в коде и не в БД в открытом виде |
| FR-LLM-10 | Тела запросов по умолчанию не логируются (только метаданные) — защита коммерческой тайны |
| FR-LLM-11 | Запрет обучения сторонних моделей на данных заказчика зафиксирован в контракте и настройке провайдера |
| FR-LLM-12 | Переключение модели для задачи фиксируется в журнале задачи (какая модель и версия промпта дали результат) |

## 19.2 Роли моделей

| Роль | Класс | Пример | Что делает |
|---|---|---|---|
| Основная рабочая | Локальная | Qwen2.5-32B-Instruct (vLLM) | Извлечение, черновики КС-2/АОСР, рутина — 67 % вызовов, стоимость 0 ₽ |
| Мультимодальная | Локальная | Qwen2.5-VL-32B | Сканы, сертификаты, redline |
| Тяжёлые рассуждения | РФ-облако | GigaChat Pro | Проверка актов, длинные тексты без КТ/ПДн |
| Резерв | РФ-облако | YandexGPT Pro | Fallback при недоступности |
| Внешние API | — | — | Запрещены для реальных данных; только R&D на синтетике |

## 19.3 Правила маршрутизации (первое совпавшее правило применяется)

| Условие | Маршрут |
|---|---|
| `data_class` = коммерческая тайна или ПДн | только локальная модель |
| Задача с изображениями (redline, сертификат, скан) | локальная мультимодальная |
| Сложная проверка акта, письма, риски графика, данные не чувствительные | РФ-облако → локальная |
| Классификация, извлечение полей, парсинг журналов | только локальная (дёшево и быстро) |
| По умолчанию | локальная |

Проверка маршрута до запуска: `POST /llm/routing/preview` — возвращает правило, выбранную модель, цепочку fallback и оценку стоимости.

## 19.4 Приёмка новой модели (обязательно до включения)

| Проверка | Порог |
|---|---|
| Валидность JSON по схеме | ≥ 99,5 % |
| Точность вызова инструментов (tool-calling) | ≥ 98 % |
| Качество русского языка (внутренняя шкала) | ≥ 8 / 10 |
| Дословность цитат в нормативных ответах | ≥ 99 % |
| Задержка p95 | ≤ 20 с |
| Стоимость одного черновика КС-2 | ≤ 6 ₽ |
| Затем | полный прогон `test`-среза golden set + подпись методолога |

## 19.5 Пример экономики (расчёт на месяц, 41 260 вызовов)

| Статья | Значение |
|---|---|
| Доля вызовов на локальных моделях | 67 % → 0 ₽ |
| Стоимость облачных вызовов | ≈ 8–10 тыс. ₽/мес при текущих ценах провайдеров |
| Экономия за счёт маршрутизации | −41 % к сценарию «всё в облако» |
| Экономия за счёт кэша | −18 % повторных вызовов |
| Контроль | лимит 60 тыс. ₽/мес, предупреждение на 80 %, стоп на 100 % |

## 19.6 Приёмочные критерии раздела 19

| ID | Критерий | Метод проверки |
|---|---|---|
| AC-LLM-01 | Новая модель подключается изменением конфигурации и проходит приёмку без правки кода | Демонстрация на тестовой модели |
| AC-LLM-02 | Попытка отправить документ класса «КТ» во внешний API блокируется; в журнале — инцидент | Автотест + проверка ИБ |
| AC-LLM-03 | При превышении лимита бюджета внешние вызовы прекращаются, система продолжает работу на локальных моделях | Тест с искусственным исчерпанием лимита |
| AC-LLM-04 | При отказе провайдера задача уходит в fallback, затем человеку; «пустой» результат не подменяется догадкой | Тест недоступности |
| AC-LLM-05 | Каждый вызов отражён в `llm_call_log` с провайдером, промпт-версией и стоимостью | Проверка выборки 100 вызовов |
| AC-LLM-06 | Стоимость за месяц по журналу совпадает со счётом провайдера с точностью ≥ 95 % | Сверка со счётом |
