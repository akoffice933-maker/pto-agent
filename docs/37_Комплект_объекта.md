# Круг 13. Комплект объекта: один прогон, одна папка, один вердикт

Двенадцать кругов дали двенадцать реестров. Но сдаётся не реестр — сдаётся **комплект по
объекту**. Проверяющий не спрашивает «есть ли у вас журнал верификации»: он спрашивает «можно ли
принять комплект». Этот круг собирает все разделы одной командой, в одну папку, и считает один
вердикт — `can_submit`.

## 1. Пробел, который воспроизводился

| Что происходило | Чем это плохо |
|---|---|
| Шесть реестров лежали в шести папках, каждый — «в целом нормально» | «в целом нормально» не существует: комплект либо полный, либо его нет |
| Раздел, который забыли собрать, выглядел как отсутствующий файл — и о нём просто не вспоминали | отсутствие журнала верификации на приёмке обнаруживается первым делом, и это уже не «мелочь» |
| Раздел исключали «по-тихому», потому что «по этому акту не надо» | исключение без основания — то же сокрытие: через месяц никто не помнит, почему его нет |
| Реестры были собраны, но не подписаны, а комплект предъявляли | неподписанный реестр в комплекте — это пачка бумаги, а не документ |
| Блокеры расписывали словами в письме: «в основном готово, кроме мелочей» | инженер не видит, что именно мешает, не открывая восемь файлов |

## 2. Что сделано

Новый модуль `pto_agent/pack.py` (схема `pto-agent/object-pack@1`), CLI `pack build --config`,
MCP-инструмент `object_pack` (33-й), 13 страж-тестов и сквозной скрипт `scripts/check_pack.py`.

### Конфиг комплекта — один файл на объект

```json
{
 "object_name": "ЖК «Северный», корпус 2",
 "number": "К-38",
 "sections": {
  "journals_work":        {"entries": "data/demo/journals/work_entries.json", "acts": "data/demo/acts/acts.json"},
  "journals_verification":{"records": "data/demo/journals/verification.json", "writeoffs": "data/demo/consumption/writeoffs.csv"},
  "quality_docs":         {"documents": "…/documents.json", "requirements": "…/requirements.json", "usage": "…/usage.json"},
  "rd":                   {"transmittals": "…/transmittals.json", "revisions": "…/revisions.json", "works": "…/works_rd.json"},
  "submittals":           {"submittals": "…/submittals.json"},
  "letters":              {"letters": "…/letters.json"},
  "involvement":          {"records": "…/involvement.json"},
  "quality_days":         {"events": "…/quality_days.json"},
  "checklists":           {"enabled": false, "reason": "чек-листы по этому акту выпускаются отдельно (письмо № 231)"}
 }
}
```

Каждый раздел собирается **тем же модулем и теми же проверками**, что и в отдельном круге:
журналы — `journals.py`, документы качества — `quality_docs.py`, РД и согласование —
`docflow.py`, письма и участники — `correspondence.py`, чек-листы — `checklist.py`. Поэтому
сводный отчёт физически не может быть «чище» разделов, и тест это фиксирует: коды находок
раздела в комплекте совпадают с кодами отдельного реестра.

Можно передать и **готовый подписанный реестр** ссылкой `{"registry": "…json"}`: тогда подпись
проверяется, а не пересобирается — правка после подписи «разваливает» раздел и он снова попадает
в блокеры.

### Пять правил вердикта

1. **Отсутствующий раздел — «нет данных», а не «пройдено».** `SECTION_MISSING` — блокер с
   названием раздела. Нет источника — значит комплект неполный.
2. **Исключить раздел можно только с основанием.** `SECTION_DISABLED_WITHOUT_REASON` — блокер;
   исключённый раздел остаётся в описи со статусом «исключён человеком» и причиной.
3. **Ошибка в любом разделе блокирует сдачу.** `SECTION_ERRORS` с числом находок и первой
   строкой текста.
4. **Сдаётся только подписанное.** `SECTION_UNSIGNED` — блокер: агент не подписывает, подпись
   ставит человек с ФИО и ролью.
5. **Пустой раздел — находка.** Собран, но записей нет — `SECTION_EMPTY`, а не «ок».

Плюс `can_submit` даёт причины отказа списком: «разделов без данных: …», «разделов с ошибками:
Журнал верификации (2), Документы качества (8) …», «не подписано разделов: …».

```
Комплект исполнительной документации по объекту: ЖК «Северный», корпус 2 · комплект К-38
  разделов: 9 · без ошибок: 1 · с ошибками: 7 · нет данных: 0 · исключено: 1 · подписано: 0
  ⚠ Общий журнал работ                        есть предупреждения
  ✗ Журнал верификации                        есть ошибки
  ✗ Документы качества на материалы           есть ошибки
  ✗ Выдача рабочей документации               есть ошибки
  ✗ Согласование исполнительной документации  есть ошибки
  ✗ Письма и запросы                          есть ошибки
  ✗ Лаборатории и геодезисты                  есть ошибки
  ✗ Авторские дни и дни качества              есть ошибки
  – Чек-листы выполненных работ               исключён человеком · чек-листы по этому акту…
  предъявлять нельзя:
     · разделов с ошибками: Журнал верификации (2), Документы качества (8),
       Выдача РД (5), Согласование ИД (5), Письма и запросы (4), Лаборатории (1), Дни качества (2)
     · не подписано разделов: все восемь собранных
```

Итог демо: **27 находок по объекту**, вердикт «предъявлять нельзя», и в отчёте перечислено ровно
то, что нужно сделать (что закрыть, что подписать).

Второй сценарий — **чистый комплект**: восемь разделов собраны без ошибок, подписаны начальником
ПТО, чек-листы исключены с причиной → `can_submit: да`. Он прогоняется в CI скриптом
`scripts/check_pack.py`: там же проверяется, что подправленный после подписи реестр снова
попадает в блокеры.

Артефакты одной командой в `out/pack/`: JSON, Markdown, XLSX (листы «Разделы», «Блокеры»,
«Находки»), DOCX-**опись комплекта** с местами подписей «подготовил / проверил / принял», плюс
все реестры разделов в той же папке.

## 4. Как пользоваться

```bash
# весь комплект по объекту одной командой
python3 -m pto_agent pack --out out/pack build --config data/demo/pack/pack.json

# код возврата: 0 — комплект предъявляется, 2 — есть блокеры
```

Порядок работы на объекте: собрать → разобрать блокеры по разделам → исправить → подписать
каждый реестр человеком → запустить `pack` снова, теперь по ссылкам `registry` — и получить
вердикт «можно предъявлять».

MCP: `object_pack` (`config` или `config_path`), 32 → **33 инструмента**,
`prompts/tools_schema.json` версии 2.4.0 (в круге 14 — 2.5.0).

## 5. Страж-тесты и CI

`tests/test_pack.py` — **13 тестов**: раздел без источника — «нет данных» и блокер; исключение без
причины — блокер; ошибки раздела блокируют сдачу; неподписанный раздел блокирует сдачу; чистый
подписанный комплект предъявляется; подпись проверяется (правка после подписи аннулирует раздел);
пустой раздел — находка; коды находок раздела совпадают с отдельным реестром; файлы и
формулировки; демо-комплект со всеми блокерами; CLI и MCP через stdio.

`scripts/check_pack.py` — **23 правила** в CI:

```
комплект объекта: правил 23 · разделов 9 · находок в демо-комплекте 27 ·
чистый комплект: разделов без ошибок 8, подписано 8 · вердикт демо-комплекта: нельзя
нарушений: 0
```

## 6. Чего комплект не делает

- **Не подписывает и не согласовывает.** Подпись ставит человек; комплект показывает, чего не
  хватает для сдачи, а не «готово».
- **Не скрывает пробелы.** Раздел без источника — «нет данных». Исключение — только с
  основанием и на виду.
- **Не заменяет решение заказчика.** Вердикт `can_submit` — это проверка полноты и подписей, а
  не приёмка работ. Принимает заказчик и технадзор.
- **Не собирает данные за инженера.** Комплект — это сумма уже существующих источников; если
  источник не заведён, комплект так и скажет.
