## 2. Форматы ФНС (XSD 5.07, РСВ)

**Первоисточник — только ФНС.** Каталог `https://format.nalog.ru/spr_data.xml` отдаёт
список «приказ → тип документа → ссылка на XSD», например
`nds/d/2020/NO_NDS_1_003_00_05_07_01.xsd`. Из песочницы сайт недоступен (TLS обрывается
на `unexpected eof while reading`), то есть схемы скачиваются в среде с доступом — и это
правильно оформлять отдельным шагом, а не тянуть в CI.

Правило, которое беру: **схему не храним в репозитории**. Копия схемы в репозитории
устаревает молча и создаёт ложное чувство проверенности. Валидация — отдельным шагом:
`xmllint --schema`, схема скачана по ссылке из каталога на дату отчёта.

Из проектов:

- **Dectron807/EdoXmlGenerator** (MIT, C#, ★2) — «Глав.Документ»: 50 форм первички, УПД
  по формату 5.03, валидация по XSD. Берём приём «шаблон + валидация перед выгрузкой» и
  идею состояний «черновик → проверен по схеме → готов к отправке». Код не берём: .NET/WPF.
- **MaxiStyle/russian-etrn-builder** (MIT, PHP) — как раскладывают «формат → версия →
  обязательные блоки» в конфиге. Полезно для нашей структуры `forms`.
- **AnyKey1/xsd-viewer** (без лицензии) — как читать ошибки валидации больших схем ФНС.
  Только идея, код копировать нельзя.

## 3. Налог на прибыль и налог на имущество

Прямых аналогов в опенсорсе **нет**. Единственный найденный проект про декларацию РФ —
**SorokaUP/NdByNds** (MIT, C#, ★1), и он про НДС. Зарубежные tax-движки не подходят:
другая нормативная база.

Значит, считаем сами, и это надо сказать прямо: здесь мы не «взяли готовое», а пишем по
форме. Что нужно для прибыли минимально честного результата:

1. доходы по 90.01 (без НДС) и расходы по 90.02/26/25/20.01 из журнала — у нас есть;
2. внереализационные — нет, значит «не включено» с причиной;
3. ставки 8 % / 17 % и распределение по бюджетам — данные, а не код;
4. убыток прошлых лет (приложение 4 к листу 02) — нет данных, «не включено»;
5. итог сверяется с 99 и 68.04: если не сходится — расхождение, а не подгонка.

Для имущества данных ещё меньше: основных средств в контуре нет вообще (нет ни 01, ни 02),
поэтому налог на имущество остаётся **«не включено: нет учёта ОС»**, а не «примерно 2,2 %».
Это честнее, чем цифра из воздуха.

## 4. НДС с авансов отдельными строками

Специализированных проектов не нашлось. Что уже есть у нас: авансы живут на 62.02
(полученные) и 60.02 (выданные), зачёт авансов реализован в казначействе. Не хватает
разделения налога:

- налог с полученного аванса начисляется отдельно (в 94н это 76.АВ; у нас роль играет 62.02);
- вычет по отгрузке — отдельно (76.ВА ≡ 62.01);
- **суммы не сворачиваются**: если свернуть, декларация сойдётся по итогу и будет неверной
  по строкам — ровно та ошибка, которую ловит наш `VAT_RATE_STALE`, только тише;
- проверка: «начислено с аванса = вычет при отгрузке в том же квартале», иначе налог
  задваивается.

Номера строк раздела 3 помечены **«на проверку»**: форма менялась приказом от 18.12.2025,
и брать номера из головы нельзя.

## 5. Больничные, отпускные, премии по приказам

Тут проекты реально помогают — но только формулами и тест-кейсами:

- **babamurad/Salary** (MIT) — стаж 60/80/100 % (до 5 лет / 5–8 / свыше 8), производственный
  календарь, расчёт от МРОТ при малом заработке. Берём проценты как данные справочника и
  кейсы «мало заработал → считаем от МРОТ 27 093 ₽».
- **EgorPoprotskiy/EyeOfWages** (MIT) — средний дневной заработок за 12 месяцев и
  **исключаемые периоды** (больничные, прошлые отпуска). Это главная причина неверных
  отпускных, и логику стоит взять.
- **NlightN22/Salary** (MIT) — структура расчётного листка «начисление / удержание / к выплате».

**Но модель придётся менять, и это главное открытие.** С 2026 работодатель начисляет
больничные только за **первые 3 дня** своей болезни; остальное платит СФР напрямую.
Значит, в ведомости Т-51 появляется строка «пособие за счёт работодателя (3 дня)»,
НДФЛ удерживается с неё, взносы **не** начисляются, а в 6-НДФЛ и РСВ попадает только эта
часть. Всё, что сверх трёх дней, в нашем контуре не считается — и это должно быть написано
на экране, а не выясняться при сверке с СФР.

Премии по приказам — не найденный код, а вопрос данных: нужен приказ (номер, дата,
основание), иначе премия — это «примерно». Поэтому: проводки по премии делаем только при
наличии приказа, без приказа — «не включено».

## 6. Реальные ключи УКЭП

- **CryptoPro/pycades** — официальное расширение CAdES. Это **зависимость**, а не код:
  требует установленного КриптоПро CSP, лицензии и контейнера с ключом. GitHub не
  распознал лицензию (`NOASSERTION`) — перед сборкой читать `LICENSE` в репозитории.
- **devind-team/CryptoPro-pycades** (MIT, ★25) — самый полезный: Dockerfile с CSP 5 +
  pycades + FastAPI-сервис подписи. Отсюда берём **архитектурное решение**: криптография
  живёт отдельным сервисом, а не внутри MIT-контура. Наш контур остаётся чистым, ключи —
  снаружи, контракт «файл → `.sig`» по HTTP.
- **JustUnknownDude/CryptoPro5docker** (без лицензии) — только как справка по пакетам.
- **Keyintegrity/pycryptoprosdk** (★37, без лицензии) — шире доступ к CSP, но код брать нельзя.
- **kuznetsovin/py_cpcsp** (MIT) — пример проверки подписи отдельно от подписания; нужно для
  нашего `verify_file`.

Наш `sign.py` уже написан под интерфейс pycades и честно отвечает «подпись недоступна»,
пока CSP нет. Следующий шаг — сервис подписи по образцу devind-team, но это требует
лицензии КриптоПро: без неё «реальные ключи» не заработают никаким кодом.

## 7. Боевой ящик Диадока

- **diadoc/diadocsdk-java**, **-csharp**, **-cpp** — официальные SDK, MIT. Используем как
  эталон модели вызовов (авторизация, PostMessage, GetMessage) и статусов документа.
  Наш клиент сверен с этой моделью.
- **developer.kontur.ru** — единственная публичная OpenAPI 3.0 спецификация среди операторов
  ЭДО (120+ методов). Когда появится боевой ящик, клиент генерируется из неё, а не пишется
  руками. Есть песочница и тестовая подпись.
- **ilyautov/business-mcp-ru** (MIT, Python) — ближайший по стеку образец: конфиг, ретраи,
  разбор ошибок API для Диадока и СБИС.
- **diadoc/integration-samples** (без лицензии) — сценарии «черновик → подпись → отправка →
  ожидание титула»; читаем.

**Условия, без которых ничего не заведётся (не код, а деньги и бумаги):** API-лицензия
около 26 900 ₽/год сверх пакетов документов, `client_id` выдаёт менеджер, подпись
формируется на нашей стороне (то есть нужен УКЭП из п. 6). Пробный доступ — 21 день.

## 8. СБИС

- **ilyautov/sbis-mcp-ru** (MIT, ★6, Python) — **45 команд**: документы, этапы, подписание,
  сертификаты, контрагенты. Единственный аккуратный публичный разбор API СБИС на Python.
  У Тензора нет OpenAPI, поэтому этот репозиторий практически заменяет спецификацию.
- **nikserg/sbis** (PHP, **GPL-2.0**) — идеи, код нельзя.
- **om1ji/om1-saby**, **Krstinov/API-SABY** — без лицензии, только чтение.
- **sbis-api-client** (PyPI, MIT, версия 0.0.3, «unverified») — как зависимость не берём:
  ноль тестов и версия 0.0.x.
- Официальный путь — **saby.ru/help** + ExtSDK2 (OLE/COM, Windows). В Linux-контейнер не
  годится, значит наш `SbisProvider` — только чистый HTTP по справочнику.

По цене СБИС дешевле Диадока (API включён в тарифы ЭДО), по разработке — дороже
(нет OpenAPI). Порядок из нашего плана («Диадок первым, СБИС вторым») этим подтверждается.

## 9. Экран налогов

Внешних образцов под российские налоги нет. Делаем сами, беря только принципы:

- строка декларации на экране показывает **источник** (счёт, проводку) и **расхождение** —
  это уже есть в `tax.to_markdown`, экран должен показывать то же самое, а не пересчитывать;
- контрольные соотношения показывать рядом со строками (идея из NdByNds);
- «не считается» — блоком на экране, как на «Зарплате», а не сноской в отчёте.

## 11. Лицензионная гигиена

Реестр проверяет политику автоматически: `copy_allowed=true` разрешён только для
MIT / Apache-2.0 / BSD / ISC / CC0. Из 27 записей **11 — «только идеи»**: GPL-2.0
(nikserg/sbis), `NOASSERTION` (pycades), «нет лицензии» (xsd-viewer, integration-samples,
CryptoPro5docker, pycryptoprosdk, om1-saby, sbis-api-client) и официальные документы ФНС.
Ни одна GPL/AGPL-запись не помечена как `library`/`dependency`.
