# Целостность цифр: `kr_pdf`, `takeoff`, `kr_schedules`, база цен

Речь не о падениях, а о худшем случае для ПТО: программа **не падает**, а выдаёт правдоподобную
неверную цифру. Каждый дефект воспроизведён на реальном вызове, потом закрыт тестом.

## 1. Корень: `float("nan")` — это «число»

Python принимает строку `"nan"` как число с плавающей точкой. Дальше по цепочке:

* объём `nan` → сумма `nan` → **итог `nan`**; отчёт печатает «nan ₽», и это не ошибка в
  понимании программы, а «всё посчитано»;
* любое сравнение с `nan` ложно, поэтому проверка «сумма по диаметрам сходится с «Итого»»
  в ведомости расхода стали **молча проходила**: `abs(nan - 1200) > 0.05` → `False`.

Проверено до исправления:

```python
# «Итого» = nan, диаметры 1200 + 800
validate_schedules(doc)  → ok: True, ни одного замечания   # ← дыра
to_boq(doc)              → «Арматура А500С — плита»: qty = nan
```

Ещё один вариант того же корня — «заполнить нулём»: неразобранный диаметр превращался в
`0.0`, и сумма «сходилась» уже с испорченной цифрой, а не с ведомостью.

## 3. Что сделано

### 3.1. Один разбор чисел на проект — `pto_agent/numeric.py`

```python
parse_number("nan")        → None     parse_number("1 234,56") → 1234.56
parse_number("inf")        → None     parse_number("−12,5")    → -12.5   # минус из PDF
parse_number("(1 234,56)") → -1234.56  # бухгалтерские скобки
positive("0,00")           → None     # ноль там, где нужен множитель, — «не заполнено»
```

`None` означает «не число» и **никогда не превращается в ноль**: ноль — это тоже данные.
Модуль используется в `kr_pdf`, `kr_schedules`, `takeoff`, `prices` — поведение одинаковое.

### 3.2. `kr_schedules`

* неразобранные диаметры выносятся отдельным замечанием `VALUE_UNPARSED` с ключом и сырым
  значением («16: «б/н»») и в сумму не входят — вместо тихого `0.0`;
* «Итого» не число → замечание `SUM_MISMATCH` с сырым значением, `ok: false`;
* если «Итого» нет или оно не число, в BOQ идёт сумма по диаметрам, строка получает
  `low` и `caveat` ««Итого» не число, взята сумма по диаметрам … нужна сверка с PDF»;
* строки спецификации/ведомости с неразобранным или нулевым количеством не исчезают молча —
  они перечисляются в замечании `QTY_MISSING` и в поле `skipped`;
* дедупликация бетона теперь учитывает конструкцию: сливаются только одна и та же конструкция
  либо строка без указания конструкции (случай «спецификация vs ведомость»); при одинаковом
  количестве у **разных** конструкций обе строки остаются с пометкой «другая конструкция».

### 3.3. `kr_pdf`

* габариты разбираются как два **положительных** размера; «12,0 х 0,0» и «12,0 х nan» больше
  не дают ни объёма `nan`, ни тишины — появляется вопрос: *«габариты в томе есть («12,0 х 0,0»,
  стр. 3), но не разобраны как два положительных размера — считать по ним нельзя»*;
* толщины плиты, стен подвала и перекрытия — тоже только положительные числа;
* расчёт, дающий 0 м³, превращается в вопрос, а не в строку с нулём.

### 3.4. `takeoff`

* несовпадение единицы объёма и единицы цены: сумма **не входит в итог**, сохраняется рядом
  как `amount_wrong_unit` («шт × ₽/м³ — не сумма»), строка → `review`;
* отрицательный объём: `review`, в итог не идёт, причина «либо возврат, либо ошибка знака»;
* одинаковые строки (элемент + единица + количество) помечаются `duplicate_of`, уходят в
  `review`; в «высокую уверенность» не попадают, их сумма видна отдельно
  (`amount_duplicates_rub`), в итоге остаётся `amount_rub` как есть — то есть итог не скрывает
  сомнительные строки, но и не выдаёт их за проверенные;
* в отчёте появился раздел «На проверку» с причиной по каждой строке и пометкой
  «**в итог не вошла**», где это так;
* в `totals` добавлены `duplicate_lines`, `negative_lines`, `wrong_unit_lines`,
  `amount_duplicates_rub` — цифры рисков видны, а не «спрятаны в логе».

### 3.5. База цен

* цена `nan`/`inf` и цена `≤ 0` — строка пропускается с причиной («цена ≤ 0» — это испорченная
  выгрузка, а не «дёшево»);
* `lookup` дополнительно не отдаёт цену, которая не число, даже если такой снимок версии уже
  лежит на диске (старые версии не переписываются — снимок есть снимок).

## 5. Что осталось (осознанно)

1. **`Decimal` вместо `float`.** Деньги и объёмы сейчас `float` с округлением на выводе.
   Для сметных сумм это допустимо (копейки сходятся), но при накоплении сотен строк и
   пересчётах лучше `Decimal` с явным контекстом. Это рефакторинг через `reconcile`,
   `takeoff`, `prices`, `export` — отдельный круг, не «попутная правка».
2. **Единицы измерения за пределами `кг → т`.** Пересчёт по коэффициентам есть только для
   килограммов; остальные несовпадения теперь ловятся (не идут в итог), но автоматического
   пересчёта «м² ↔ 100 м²» нет — его должен задавать словарь соответствий.
3. **Дубли по смыслу, а не по строке.** Ловится точное совпадение «элемент + единица +
   количество». «Бетон В25 — плита» и «Бетон В25 — плита перекрытия» дублем не считаются:
   это уже семантика, нужен словарь синонимов (в проекте есть только для кодов ресурсов).
4. **Округление объёмов до 0,1 м³ в `kr_pdf`** — как в исходной логике: это расчёт по
   габаритам с оговоркой «верхняя оценка», точность выше него не имеет смысла.
