# 18. Аудит-лог, закупка материалов и версии цен

Три шага, которые в отчёте 17 стояли первыми: журнал с автором и причиной, модуль
«заявка → сравнение КП → обоснование выбора», импорт цен с журналом версий.
Написано по итогам OSS-разведки: схема аудита — по образцу `django-simple-history`
(BSD-3, снимок «до/после» + дельта), обязательные поля оферты — из
`openprocurement.api` (Apache-2.0, раздел `tender.bids`), код этих проектов не копировался.

Проверено прогоном на демо-данных из сметы 1166/Н (объект «Дошкольное отделение»):
2 версии цен ФГИС ЦС, 7 строк КП от 3 поставщиков, 11 позиций заявки.

## 1. Аудит-лог: каждое действие с автором, причиной и основанием

Файл `pto_agent/audit.py`, журнал — JSONL с хэш-цепочкой (каждая запись хэширует
предыдущую; подмена строки ломает `verify()`).

Запись об изменении:

```json
{
  "ts": "2026-11-05T07:16:22+00:00",
  "actor": "Иванов И.И.", "actor_type": "human",
  "action": "procurement.decided",
  "entity": "procurement:ЗМ-1166/Н-1:62.1.01.09-1101",
  "payload": {
    "before": {"supplier": null, "price_vat": null},
    "after":  {"supplier": "ООО «Кабель-СПб»", "price_vat": 516.0},
    "delta":  {"supplier": {"from": null, "to": "ООО «Кабель-СПб»"},
               "price_vat": {"from": null, "to": 516.0}},
    "changed_fields": ["supplier", "price_vat"],
    "reason": "по автоматам — срок поставки 5 дней важнее 55 руб. разницы",
    "reason_missing": false,
    "ref": "out/procurement/comparison.json"
  },
  "hash": "..."
}
```

Правила, которые модуль соблюдает:

| Правило | Как реализовано |
|---|---|
| Видно не только «что», но и «было/стало» | `before` + `after` + `delta` только по изменившимся полям (`diff()`) |
| Причина обязательна | `reason` пишется всегда; если пусто — `reason_missing: true`, и это видно в ленте и в выгрузке |
| Основание — ссылкой | `ref`: файл сравнения, номер КП, пункт нормы |
| Автор и его роль | `actor` + `actor_type` (`human` / `agent` / `system`) |
| Журнал нельзя незаметно переписать | хэш-цепочка, `verify()` → `(ok, записей, 'цепочка целостна')` или «хэш не совпадает» с номером строки |
| Ничего не удаляется | лента только растёт; «удаление» — это запись с `after: {deleted: true}` |

Что пишется в журнал сейчас: импорт версии цен (`prices.imported`), решение по
поставщику (`procurement.decided`), операции с чертежом (существовавшие). Лента читается
человеком: `pto_agent audit list` печатает «когда / хэш / кто / что / где / какие поля /
причина», `audit export` выгружает в xlsx.

```bash
python3 -m pto_agent audit --path out/procurement/audit.jsonl list
python3 -m pto_agent audit --path out/procurement/audit.jsonl list --entity procurement:ЗМ-1166/Н-1:62.1.01.09-1101
python3 -m pto_agent audit --path out/procurement/audit.jsonl show 1a289f4b1e25
```

## 2. Закупка: заявка → сравнение КП → решение человека

Файл `pto_agent/procurement.py`. Три шага, каждый — отдельный файл, чтобы решение можно
было перепроверить через месяц.

### 2.1. Заявка из сметы

`request_from_estimate()` берёт материалы из сметы (в том числе выгрузку АРОС),
работы отбрасывает и **склеивает одинаковые коды** в одну позицию: в смете 1166/Н кабель
ВВГнг 3х1,5 стоит двумя строками (участки), закупать его двумя лотами бессмысленно.

Демо: 47 позиций сметы → **11 позиций заявки** (14 строк материалов, три кода встречались
дважды). Количество суммируется, ссылка на исходные строки сохраняется (`lines`).

### 2.2. Сравнение КП: какие предложения вообще можно сравнивать

Обязательные реквизиты КП взяты из схемы оферты `openprocurement.api`:
**поставщик, код ресурса, цена, единица, срок поставки, срок действия цены, дата КП,
номер КП**. Нет любого — предложение не участвует в сравнении, а попадает в
`not_comparable` с перечнем недостающих полей и причиной.

Отдельно проверяется, что КП не просрочено (срок действия на дату сравнения) и что
единица измерения совпадает с заявленной.

Приведение к одной базе: цена каждого КП пересчитывается в цену с НДС
(`price_vat`), база сравнения пишется словами (`с НДС 20%` / `без НДС`) — иначе КП
упрощенца за 64 800 ₽ «выигрывает» у КП с НДС за 81 000 ₽ просто потому, что в нём нет
налога. Сортировка: цена, затем срок поставки (`--prefer delivery` меняет приоритет).

Демо-результат (`out/procurement/comparison.json`):

| Что | Значение |
|---|---|
| Статус | `partial` (покрыты 3 позиции из 11) |
| Сумма по предложениям | **34 900,32 ₽** |
| Экономия против худшего пригодного КП | **13 079,76 ₽** |
| Не участвовали в сравнении | 1 КП — «СнабМонтаж»: нет срока действия цены |
| Без пригодных предложений | 8 позиций — `no_quotes`, с причиной «предложений по позиции нет» |

Строка сравнения всегда содержит **обоснование словами**: «минимальная приведённая цена
64 800,00 ₽ (без НДС) у «ООО «ЭлектроТорг»»; срок поставки 14 дн.; цена действует до
2026-11-20; следующее предложение «ООО «Кабель-СПб»» дороже на 32 400 ₽/1000 м».

### 2.3. Решение: за человеком

`decide()` не выбирает поставщика — он **фиксирует выбор человека**. Требуется `--by`
(ФИО) и `--reason`. Если человек выбрал не лучшего по цене, считается `over_best` —
насколько дороже лучшего предложения и по каждой позиции отдельно.

Выбрать поставщика, который не подавал пригодного КП, нельзя: такой выбор отклоняется
с причиной (`problems`), а не «принимается молча». Все решения уходят в журнал аудита
одной записью на позицию: автор, роль, причина, ссылка на сравнение.

Демо: по кабелю выбран минимум цены, по автоматам — поставщик с поставкой за 5 дней
вместо 12 (**+840 ₽**, это видно в решении и в выгрузке). Итог: 2 позиции на **34 645,92 ₽**.

### 2.4. Что выдаётся на руки

- `out/procurement/request.json` — заявка;
- `out/procurement/comparison.json` + **`comparison.xlsx`** — сравнение по позициям, непригодные КП с причинами, лист «решение»;
- `out/procurement/decision.json` — решение человека;
- `out/procurement/procurement.md` — отчёт «почему так» для согласования.

```bash
python3 -m pto_agent procure --out out/procurement request \
  --smeta uploads/smeta_1166N_AROS.md --object-name "Дошкольное отделение" \
  --request-no "ЗМ-1166/Н-1" --need-by 2026-11-20

python3 -m pto_agent procure --out out/procurement --audit out/procurement/audit.jsonl \
  compare --request out/procurement/request.json --quotes data/demo/quotes/quotes_1166n.csv

python3 -m pto_agent procure --out out/procurement --audit out/procurement/audit.jsonl \
  decide --request out/procurement/request.json --quotes data/demo/quotes/quotes_1166n.csv \
  --choose "62.1.01.09-1101=ООО «Кабель-СПб»" --by "Иванов И.И." \
  --reason "срок поставки 5 дней важнее 55 руб. разницы"
```

## 3. Цены: каждая выгрузка — версия, каждый ответ — с датой

Файл `pto_agent/prices.py`. Никакой «текущей цены» в системе нет — есть версии.
Импорт выгрузки (xlsx/csv) создаёт снимок `prices_{дата}-{источник}[-{регион}].json`,
digest sha256 первых 16 символов, запись в `index.json` и запись в журнал аудита
(кто импортировал, что, откуда, сколько позиций), с предупреждением, если версия на эту дату
уже была.

Правило, которое важнее всего: **`lookup(as_of=...)` не отдаёт выгрузку новее запрошенной
даты**. Расчёт акта за сентябрь не должен опираться на декабрьский прайс. Если цены в
доступных версиях нет — `found: false`, перечень просмотренных версий и явная пометка
«похожий ресурс не подставляется».

Демо (2 версии ФГИС ЦС, 9 ресурсов, регион 47):

| Запрос | Ответ |
|---|---|
| автомат 1P 16A на 2025-10-01 | **410 ₽** из версии `2025-09-01-фгис-цс-47` |
| тот же код на 2025-12-31 | **459 ₽** из версии `2025-12-01-фгис-цс-47` |
| история | +49 ₽ (+11,95 %) — рост в IV квартале |
| несуществующий код | `found: false`, обе версии в списке просмотренных |

```bash
python3 -m pto_agent prices --out data/prices --audit out/audit.jsonl \
  import --file data/demo/prices/fgis_cs_2025q3.csv --source "ФГИС ЦС" \
  --date 2025-09-01 --region 47 --zone 1
python3 -m pto_agent prices --out data/prices lookup --code 62.1.01.09-1101 --as-of 2025-10-01
python3 -m pto_agent prices --out data/prices history --code 62.1.01.09-1101
python3 -m pto_agent prices --out data/prices list
```

## 4. MCP: те же три шага доступны агенту

Инструментов стало **20** (было 17): `prices` (import / lookup / history / list),
`procurement` (request / compare / decide), `audit_trail` (list / show / verify).
Схемы — в `prompts/tools_schema.json` (v1.3.0), классы побочных эффектов:
`prices` и `procurement` — `write`, `audit_trail` — `read`.

Важное ограничение в самих инструментах: `procurement` не умеет «выбрать сам» — только
`compare` (расчёт) и `decide` (запись решения человека с ФИО и причиной). Агент может
подготовить сравнение и обоснование, но подпись под выбором поставщика ставит человек.

## 6. Границы: чего здесь нет и почему

| Чего нет | Почему |
|---|---|
| Автоматического доступа к API ФГИС ЦС и индексам Минстроя | Публичного машиночитаемого API нет — только выгрузки; модуль принимает выгрузку и требует источник и дату |
| Автоматического выбора поставщика | По принципу «человек в контуре»: агент готовит сравнение и обоснование, выбор фиксируется человеком |
| Рейтинга поставщиков и истории неисполнения | Нет источника; когда появится свой реестр договоров — станет следующим шагом |
| Расчёта сметной стоимости и индексов пересчёта | Это отдельный слой (ФСНБ-2022), в OSS его нет, а «на глаз» такие цифры не считаются |
| Склада и партий/сертификатов | Слой закрывается InvenTree (MIT) — интеграция, не свой код |

**Что нужно от вас для следующего шага:** одна реальная выгрузка ФГИС ЦС (или КП
поставщика) — на ней проверю чтение колонок и спрошу про поля, которых не хватает;
и решение, кто в фирме имеет право нажимать «решил» (роль в журнале).
