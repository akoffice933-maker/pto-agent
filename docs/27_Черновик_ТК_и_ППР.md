# Черновик ТК и ППР: что агент заполняет, а что запрашивает

**Дата:** 6 ноября 2025 г. Продолжение `docs/26_ТК_и_ППР_открытый_код`: раз готового OSS нет,
ТК и ППР собираются своими силами — на матрице требований и нормативной базе агента.

Модуль: `pto_agent/tk.py`. Команда: `python -m pto_agent tk draft | ppr | confirm`.
Тесты: `tests/test_tk.py` (20).

---

## 1. Главное решение: чего в документе не будет

ТК и ППР — документы, где выдумать опаснее всего: состав операций, допуски, схемы
механизации, охрана труда, трудозатраты. Поэтому разделы делятся на три вида, и это видно
в самом документе:

| Вид раздела | Чем заполняется | Пример |
|---|---|---|
| **Из данных агента** | матрица требований, классификатор, нормативная база, переданная смета | вид работ, скрываемость, комплект ИД, протоколы, нормы (со сверкой) |
| **Из документа-источника** | позиции сметы с пометкой «перенесено, проверить» | раздел «Материалы» — если смета передана |
| **Запрос человеку** | `needs_input` с адресатом | состав операций (технолог), машины (механик), ОТиПБ (специалист по ОТиПБ), трудозатраты (сметчик) |

Нормы — отдельная история. Каждая берётся из матрицы и **сверяется с загруженной нормативной
базой**, три исхода:

1. документ и пункт есть в базе → `verified: true`, приводится цитата (и страница, если есть);
2. документ есть, пункта нет → «документ в базе есть (ред. …), пункта X в ней нет — проверить»;
3. документа нет → «документа нет в загруженной нормативной базе — проверить».

В тексте и в DOCX у непроверенной нормы стоит **«не проверено по нормативной базе»**, а в
таблице — колонка «Сверено с базой». Норма «по памяти» в документ не попадает.

## 2. Структура ТК (8 разделов)

| Раздел | Состояние |
|---|---|
| 1. Область применения и границы работ | объект, вид работ, скрываемость — из данных |
| 2. Нормативные ссылки | из матрицы + сверка с базой |
| 3. Состав и последовательность операций | **запрос:** технолог / главный инженер |
| 4. Материалы, изделия и оборудование | из сметы (с пометкой) либо запрос |
| 5. Машины, механизмы, инструмент | **запрос:** механик участка |
| 6. Контроль качества и ИД | из матрицы: акты, схемы, журналы, протоколы |
| 7. Охрана труда, пожарная и экологическая безопасность | **запрос:** специалист по ОТиПБ |
| 8. Калькуляция трудозатрат | **запрос:** сметчик (норм времени в базе нет) |

Раздел 6 — то, чего нет ни у одного OSS из обзора: комплект ИД по виду работ выводится из
матрицы, а не из шаблона.

## 3. Структура ППР (10 разделов)

ППР — документ по объекту, поэтому заполняются только общие данные и перечень ТК
(виды работ распознаются по смете тем же классификатором, что и для актов). Остальные
разделы — запросы с конкретным адресатом и формулировкой: не «нужен стройгенплан», а «нужен
план площадки с механизмами, складами и временными сетями (из ПОС/ППР проектировщика)».
Раздел «Технология производства работ» намеренно не пересказывается: он раскрывается
технологическими картами.

## 4. Статус документа и подтверждение

* `draft_unapproved` — «черновик, не проверен человеком»;
* подтверждение требует **ФИО и роли**, анонимное не принимается (иначе это не HITL, а кнопка);
* инженер вписывает разделы через `--filled` (JSON `{раздел: [текст, …]}`); каждый внесённый
  пункт помечается «внесено человеком (ФИО)» — агент их не переписывает и не дополняет;
* после подтверждения статус `draft_confirmed_by_human` — по-русски это **«черновик проверен
  инженером (не утверждённая ТК)»**; слов «готова к применению» в документе нет, и тест это
  проверяет;
* подтверждение пишется в журнал аудита (`tk.confirmed`, кто, роль, причина, сколько внесено,
  сколько разделов осталось без данных).

## 5. Как выглядит результат

```
$ python -m pto_agent tk --out out/tk --audit out/tk/audit.jsonl draft \
    --work-type earthworks --object-name "Школа на 550 мест"

Черновик технологической карты: Школа на 550 мест
  вид работ: Земляные работы (разработка котлована, обратная засыпка)
  разделов: 8 · заполнено: 9 · требуют данных: 5
  нормы: проверено 0 из 2
    ⚠ состав и последовательность операций → перечень операций с допусками и схемами — технолог / главный инженер
    ⚠ машины, механизмы и инструмент → перечень машин и механизмов с обоснованием — механик участка
    ⚠ требования охраны труда… → раздел ОТиПБ под объект — специалист по ОТиПБ
    ⚠ калькуляция трудозатрат → калькуляция по ГЭСН/ФЕР или хронометражу — сметчик
  файлы: out/tk/tk_draft.json, out/tk/tk_draft.docx
  это черновик: не утверждённая ТК, подписывает ИТР после проверки
```

Три файла: `tk_draft.json` (машинный, для MCP и повторной сборки), `tk_draft.md` (чтение),
`tk_draft.docx` (для инженера: разделы, пометки «НУЖНЫ ДАННЫЕ», таблица состояния норм,
место для подписи).

Проверка на живом примере: норма `СП 45.13330.2017, п. 6.1.2` из матрицы в базе отсутствует →
в документе она помечена как непроверенная. Загруженный фрагмент ПУЭ-7 (п. 1.8.37) —
проверяется с цитатой, это проверено тестом `test_norm_present_in_base_is_verified_with_quote`.

## 6. Что осталось (честный список)

1. **Состав операций.** Агент его не заполняет и не будет, пока нет источника: либо инженер,
   либо типовые карты заказчика, загруженные как нормативная база. Это следующий шаг, и он
   требует данных от вас, а не кода.
2. ~~**MCP-инструмент.**~~ **Сделано:** инструмент `tk_draft` (23-й) с действиями
   `draft` / `ppr` / `confirm`; прогон по всем видам работ — `docs/28`.
3. **Реестр ТК объекта.** Сейчас каждая ТК — отдельный черновик. Реестр «объект → ТК →
   статус → кто проверил» логично собрать как продолжение `portfolio.py`, но это уже учёт,
   а не документ.
4. **ППР как комплект.** ППР обычно включает график и стройгенплан из ПОС; пока агент честно
   запрашивает их, а не рисует.
5. **Нормативная база.** Пока в ней один фрагмент (ПУЭ-7, пп. 1.8.37 и 1.8.39). Чем больше
   СП загружено с пунктами, тем больше норм в ТК станут «сверено», вместо «не проверено».
   Это работа с данными, не с кодом.
