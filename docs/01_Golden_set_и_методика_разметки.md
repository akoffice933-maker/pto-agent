# 1. Назначение

Golden set решает три задачи, без которых проект нельзя ни принять, ни защитить:

1. **Измеримость.** Метрики из раздела 13 ТЗ (F1 0,95 / точность цитат 99 % / галлюцинации ≤ 0,5 %) проверяются только на размеченных данных, а не на «пяти показательных примерах».
2. **Защита от регрессий.** Любое изменение модели, промпта, парсера или нормативной базы прогоняется на golden set. Если качество падает — релиз блокируется.
3. **Договорная база.** Приёмочные испытания проводятся сравнением с golden set, а не с субъективным мнением. Это снимает спор «работает / не работает» между заказчиком и исполнителем.

**Ключевое правило:** golden set — собственность компании-заказчика, хранится в закрытом контуре, не передаётся вендору модели и не используется для обучения без письменного разрешения.

## 2.2 Требования к отбору (обязательно отражаются в паспорте выборки)

| Признак | Требование к покрытию |
|---|---|
| Качество источника | ≥ 30 % сканов без текстового слоя, ≥ 10 % плохого качества (перекос, низкий контраст) — именно на них агент ломается |
| Виды работ | ≥ 6 видов: земляные, бетонные, монтаж трубопроводов, кровля, электромонтаж, отделочные |
| Роль документа | есть документы и от генподрядчика, и от субподрядчиков |
| Заказчик | ≥ 2 разных заказчика с разными требованиями к ИД |
| Период | ≥ 2 отчётных периода по одному объекту (проверка накопительного учёта) |
| Язык/формат | только русский, но разные шаблоны (Word, Excel, выгрузки Гранд-Смета) |
| Отрицательные примеры | ≥ 20 % документов с ошибками: отсутствие подписи, неверные даты, дубли, завышенные объёмы |
| «Чистые» примеры | ≥ 30 % полностью корректных документов (проверка на ложные срабатывания) |

**Запрещено:** включать в выборку документы, созданные самим агентом (утечка), и документы, которые уже использовались для настройки промптов при финальной проверке (см. раздел 8).

# 5. Процедура разметки

1. **Инвентаризация.** Сбор документов по Приложению E ТЗ, присвоение ID, занесение в паспорт выборки (источник, тип, качество, объект, вид работ).
2. **Подготовка.** Обезличивание, разбиение PDF на страницы, нормализация имён файлов (`GS-01-A-014_ks2_2026-09.pdf`).
3. **Пилотная разметка.** 10 % выборки размечают оба разметчика независимо → подсчёт согласия (Cohen's κ) → уточнение инструкции.
4. **Основная разметка.** Каждая единица размечается по схеме раздела 6, заполняется JSONL.
5. **Кросс-проверка.** 20 % единиц размечаются вторым разметчиком «слепо»; при κ < 0,8 инструкция переписывается, спорные единицы уходят арбитру.
6. **Валидация файлов.** Автопроверки: обязательные поля, ссылочная целостность (все cited документы существуют), суммы сходятся, нет дублей ID.
7. **Фиксация версии.** Присвоение версии `golden-v1.0`, хэш архива, запрет изменения без changelog.
8. **Приёмка.** Подпись владельца выборки, публикация отчёта о составе и согласии разметчиков.

# 6. Схемы разметки

## 6.1 GS-01 — Акты КС-2 (эталон позиций и ошибок)

Формат: один JSON-объект на акт (JSONL).

```json
{
  "id": "GS-01-A-014",
  "object_code": "OBJ-142",
  "period": {"from": "2026-09-01", "to": "2026-09-30"},
  "source_files": ["ks2_014.pdf", "smeta_v3.xlsx", "journal_sep.xlsx"],
  "positions": [
    {
      "line_no": 1,
      "estimate_code": "ФЕР 01-02-001-01",
      "name": "Разработка грунта в котловане",
      "unit": "1000 м3",
      "qty_actual": 12.4,
      "qty_estimate": 12.0,
      "price": 12500.0,
      "amount": 155000.0,
      "sources": [{"doc": "journal_sep.xlsx", "page": 1, "row": 12}],
      "has_backing_docs": true
    }
  ],
  "planted_errors": [
    {"type": "VOLUME_OVER_ESTIMATE", "line_no": 1, "note": "факт 12,4 против сметы 12,0"},
    {"type": "PRICE_MISMATCH", "line_no": 4, "note": "цена 980 вместо 1050 по смете"}
  ],
  "gold_totals": {"without_vat": 1245600.00, "vat": 249120.00, "with_vat": 1494720.00},
  "annotator": "PERSON_001",
  "kappa_check": true
}
```

**Правила:** `planted_errors` заполняется и для реально допущенных ошибок, и для искусственно внесённых (в пропорции 50/50, с пометкой `artificial: true`). Суммы пересчитываются независимо от документа (вручную или скриптом), расхождение с документом фиксируется как отдельная ошибка.

## 6.2 GS-02 — Пакеты ИД (эталон комплектности)

```json
{
  "id": "GS-02-P-003",
  "object_code": "OBJ-142",
  "work_type": "concrete",
  "profile_version": "customer-A/v3",
  "documents": [
    {"doc_type": "AOSR", "number": "АОСР-142-07", "status": "issues",
     "issue": "нет ссылки на чертежи РД", "file": "aosr_07.pdf"},
    {"doc_type": "SCHEME", "number": "ИС-142-03", "status": "present", "file": "is_03.pdf"}
  ],
  "missing": ["Протокол испытаний бетона на 28 суток"],
  "ready_for_transfer": false
}
```

## 6.3 GS-03 — Нормативные вопросы

```json
{
  "id": "GS-03-N-041",
  "question": "Какая минимальная толщина защитного слоя бетона для фундамента?",
  "as_of_date": "2026-11-02",
  "context": {"work_type": "concrete", "doc_type": "АОСР"},
  "gold": {
    "answer_type": "answer",
    "citations": [
      {"doc": "СП 63.13330.2018", "clause": "10.3.2", "edition": "с изм. 2",
       "quote_span": "…точная цитата…"}
    ]
  },
  "acceptable_alternatives": [
    {"doc": "СП 63.13330.2018", "clause": "10.3.1"}
  ],
  "forbidden": ["СНиП 52-01-2003 как действующий"],
  "difficulty": "medium",
  "annotator": "PERSON_002"
}
```

Типы вопросов (обязательные доли): прямой по действующей норме — 40 %, отменённый документ/замена — 15 %, вне базы (корректный отказ) — 10 %, дата применимости (документ прошлых лет) — 10 %, конфликт норм — 10 %, «провокация» с подменой — 5 %, многошаговый (несколько пунктов) — 10 %.

## 6.4 GS-04 — Redline-кейсы

```json
{
  "id": "GS-04-R-007",
  "drawing": "dwg_142_kzh1.dwg",
  "redline": "rl_03.pdf",
  "scale": "1:100",
  "registration": {"control_points": [[120,340],[880,340]], "residual_mm": 1.4},
  "marks": [
    {"mark_id": "m1", "bbox": [420,1180,505,1210], "class": "add_pipe",
     "params": {"diameter_mm": 150, "from": [12500,4300], "to": [12500,8700]},
     "expected_op": "ADD_POLYLINE", "confidence_gold": "clear"},
    {"mark_id": "m2", "bbox": [610,900,650,930], "class": "unclear",
     "note": "наложение текста, ожидается needs_human_decision"}
  ],
  "expected_entity_delta": {"added": 3, "deleted": 1, "modified": 2},
  "reviewer": "PERSON_003",
  "accepted_by_engineer": true
}
```

**Обязательно:** в выборке ≥ 15 % пометок класса `unclear` — проверяется главное свойство: агент не «додумывает», а выносит на человека.

## 6.5 GS-05 — Извлечение полей документов

Спаны обязательны (проверка не только значения, но и что оно взято из нужного места):

```json
{
  "id": "GS-05-D-022",
  "doc_type": "certificate",
  "file": "cert_4412.pdf",
  "quality": "scan_low",
  "fields": {
    "material_name": {"value": "Бетон B25 W6 F150", "span": {"page": 1, "bbox": [90,210,420,240]}},
    "doc_number": {"value": "№ 4412", "span": {"page": 1, "bbox": [90,260,300,285]}},
    "valid_to": {"value": "2027-02-01", "span": {"page": 1, "bbox": [300,260,470,285]}},
    "batch_no": {"value": null}
  }
}
```

## 6.6 GS-06 — Сверки объёмов

По каждому кейсу: три источника (смета, журнал, акты субподряда) + эталонный список расхождений с типами и критичностью + список допустимых (не являющихся ошибками) отклонений — для измерения ложноположительных срабатываний.

## 6.7 GS-07 — Письма и ответы на замечания

Пары «замечание технадзора → эталонный ответ» с разметкой: какие факты обязаны быть в ответе (со ссылками на документы), какие формулировки недопустимы (обещания без оснований, признание вины без проверки). Оценка — экспертная, по 5-балльной шкале, двумя экспертами.

# 7. Метрики и целевые значения

| Блок | Метрика | Формула / метод | Цель | Блокирует релиз при |
|---|---|---|---|---|
| GS-01 | Точность извлечения объёмов | F1 по позициям (qty ±0,01) | ≥ 0,95 (текст) / ≥ 0,85 (скан) | < 0,90 / < 0,75 |
| GS-01 | Выявление заложенных ошибок | recall по `planted_errors` | ≥ 0,95 | < 0,90 |
| GS-01 | Ложные срабатывания | FP / (FP + TP) | ≤ 0,10 | > 0,20 |
| GS-01 | Точность арифметики | доля актов с верными итогами | 1,00 | < 1,00 |
| GS-01 | Доля документов, принятых без правок | ручная приёмка инженером | ≥ 0,70 | < 0,50 |
| GS-02 | Полнота выявления отсутствующих документов | recall | 1,00 | < 0,95 |
| GS-03 | Точность цитирования | цитата дословно в указанном пункте | ≥ 0,99 | < 0,97 |
| GS-03 | Галлюцинированные ссылки | доля несуществующих пунктов | ≤ 0,005 | > 0,01 |
| GS-03 | Корректность ответа | совпадение с эталоном (2 эксперта) | ≥ 0,90 | < 0,80 |
| GS-03 | Корректный отказ вне базы | доля `not_found` на вопросах вне базы | ≥ 0,95 | < 0,85 |
| GS-04 | Точность классификации пометок | accuracy по `class` | ≥ 0,85 | < 0,75 |
| GS-04 | Пропуск пометок | доля не показанных человеку | ≤ 0,05 | > 0,10 |
| GS-04 | Доля схем, принятых без переработки | экспертная приёмка | ≥ 0,70 | < 0,50 |
| GS-05 | F1 по полям | по каждому типу документа | ≥ 0,92 | < 0,85 |
| GS-06 | Recall расхождений | по эталонному списку | ≥ 0,95 | < 0,90 |
| GS-07 | Пригодность черновика письма | средний балл 2 экспертов | ≥ 4,0 / 5 | < 3,5 |
| Общее | Латентность p95 | по логам | ≤ 15 с | > 30 с |

**Правило остановки:** если хотя бы одна метрика в столбце «блокирует релиз» не достигнута — релиз не выпускается, результаты выносятся на разбор с указанием, какой компонент виноват (парсер, retrieval, генерация, правила).

# 8. Разбивка данных и защита от утечки

| Набор | Доля | Использование |
|---|---|---|
| `dev` | 50 % | Настройка промптов, few-shot примеры, отладка правил — **разрешено разработчику** |
| `test` | 50 % | Только финальная проверка перед релизом — **доступ у методолога, не у разработчика** |

Правила защиты от утечки:

1. Разделение **по объектам**, а не по документам: все документы одного объекта попадают в один набор. Иначе модель «узнаёт» объект по контексту.
2. Few-shot примеры берутся только из `dev`.
3. При изменении промпта на основании ошибок `test` — этот экземпляр `test` помечается как «использованный» и заменяется новым.
4. Реестр изменений выборки (`changelog`) ведётся с указанием причины и автора.

# 9. Регламент регрессии

| Событие | Действие |
|---|---|
| Изменение системного промпта | Полная регрессия `dev`, при успехе — `test` |
| Смена версии LLM | Полная регрессия `test` + сравнение с предыдущей версией (отчёт diff по метрикам) |
| Обновление нормативной базы | Регрессия GS-03 + проверка, что новые редакции не сломали ответы по действующим нормам |
| Изменение парсеров/OCR | Регрессия GS-01, GS-05 |
| Изменение CAD-пайплайна | Регрессия GS-04 + проверка entity_count до/после |
| Плановый релиз | Полный прогон, отчёт в формате «метрика / было / стало / вердикт» |

Артефакты прогона сохраняются: версия выборки, версии моделей и промптов, вывод по каждому экземпляру, агрегированные метрики, ссылка на задачу в трекере.

# 10. Критерии приёмки этапа

1. Состав выборки соответствует разделу 2 (паспорт выборки подписан владельцем).
2. Все файлы прошли автопроверки: обязательные поля, ссылочная целостность, суммы, отсутствие дублей.
3. Cohen's κ между разметчиками ≥ 0,80 по каждому блоку (для GS-07 — ≥ 0,70).
4. Разбиение `dev`/`test` выполнено по объектам, факт зафиксирован в паспорте.
5. Настроен автоматический прогон регрессии одной командой с формированием отчёта.
6. Базовый прогон выполнен (пусть даже на baseline-модели) — есть «точка отсчёта».
7. Обезличивание проверено службой ИБ, доступ ограничен.

# Приложение. Инструкция разметчику (краткая)

1. Размечай только то, что видно в документе. Если поле не читается — ставь `null` и `"unreadable": true`, не угадывай.
2. Любое значение сопровождай ссылкой: файл, страница, координаты (bbox) или строка/столбец.
3. Числа проверяй независимым пересчётом, а не «на глаз» по итогу документа.
4. Если документ внутренне противоречив — фиксируй оба значения и добавляй `"conflict": true`.
5. Спорный случай не решай в одиночку: помечай `"needs_arbiter": true` и оставляй комментарий.
6. Не редактируй чужие разметки — создавай новый файл с суффиксом `_v2`.
7. Перед сдачей прогони `python tools/validate_gs.py <файл>` — автопроверки обязательны.
