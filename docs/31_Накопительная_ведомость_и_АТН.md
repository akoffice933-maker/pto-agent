# Накопительные ведомости и АТН на дополнительные работы

**Круг 11.** Деньги по допработам на объекте спорят чаще всего: подрядчик предъявляет их
в конце, заказчик спрашивает «где это в проекте и кто разрешил». Было: акты лежали файлами,
портфель считал деньги под риском по текущему выпуску, а накопительной ведомости и акта на
дополнительные работы не было вовсе. Стало: ведомость нарастающим итогом по позициям и АТН,
в который позиция без основания не попадает.

## 1. Воспроизведённые пробелы

**Пробел 1. Сумма акта и сумма позиций — разные числа, и это нигде не видно.**
В демо-объекте (`data/demo/acts/acts.json`) акт КС-2 №38 идёт с суммой 34 106 600 ₽, но
**без построчных позиций** (выпуск распознан, а разбивки нет). До этого круга портфель брал
сумму акта и не спрашивал, чем она подтверждена. Итог: «предъявлено 38,5 млн ₽» и
«подтверждено позициями 4,4 млн ₽» — разница 34,1 млн ₽ существовала, но не показывалась.

**Пробел 2. Накопительного итога по позиции не было.** Портфель отвечает «сколько денег под
риском», но не «сколько предъявлено по этой позиции с начала работ и сколько осталось по
смете». Отсюда два типовых вопроса без ответа: не предъявлено ли дважды и не вышли ли за смету.

**Пробел 3. Допработы предъявлялись «списком».** Не было ни структуры основания (лист РД,
схема, письмо, задание заказчика), ни правила «нет основания — нет позиции», ни защиты от
повтора внутри акта.

## 2. Что сделано

### Накопительная ведомость (`pto_agent/cumulative.py`)

Строка ведомости = код + единица. Для каждой строки: количество и сумма по периодам, итог
нарастающим итогом, объём и сумма по смете, остаток. Плюс проверки, каждая со своим кодом:

| Код проверки | Что ловит | Уровень |
|---|---|---|
| `ACT_SUM_MISMATCH` | сумма акта ≠ сумме позиций (с обеими цифрами и разницей) | ошибка |
| `DUPLICATE_ACT` | один и тот же акт внесён дважды — второй раз не суммируется | ошибка |
| `BAD_NUMBER` | `nan` или мусор в количестве/сумме — позиция не входит в итог | ошибка |
| `UNIT_MISMATCH` | один код в м² и м³ — строки разделены, суммы не складываются | ошибка |
| `NO_POSITIONS` | акт без позиций: сумма есть, подтверждения построчно нет | предупреждение |
| `SAME_PERIOD_DOUBLE` | одна позиция в двух актах одного периода — возможен двойной счёт | предупреждение |
| `NEGATIVE_QTY` | отрицательная строка — учтена как сторно | предупреждение |
| `NOT_IN_ESTIMATE` | позиции нет в смете — кандидат в АТН | предупреждение |
| `OVER_ESTIMATE` | предъявлено больше сметы — кандидат в АТН или ошибка в акте | предупреждение |

Выход: `cumulative.json`, `cumulative.md`, `cumulative.xlsx` (листы «Ведомость», «Акты»,
«Проверки»). Код возврата CLI: `0` — ошибок нет, `2` — есть ошибки; `--strict` делает
провалом и предупреждения.

### АТН (`pto_agent/atn.py`)

Позиция акта: код, наименование, единица, количество, цена, **основание** (`kind` + `ref` +
дата). Решение принимается по правилам, а не по «выглядит нормально»:

| Ситуация | Что делает модуль |
|---|---|
| есть основание и цена | позиция в акте, сумма в итог |
| нет основания (или указан только вид либо только ссылка) | в `needs_basis` со своей суммой, **в итог не входит** |
| цены нет ни в позиции, ни в смете | в `no_price`, сумма не считается (не ноль рублей) |
| цена ≤ 0 | в `no_price` |
| количество ≤ 0 или не число | в `rejected` с причиной |
| та же позиция (код + единица) второй раз в этом же акте | в `rejected`: «уже есть в этом акте (строка N)» |
| количество больше остатка по смете | позиция входит, помечается «превышает остаток по смете на X» и попадает в `excess_vs_estimate_rub` |

Подтверждение — только человеком с ФИО и ролью; статус после проверки «проверен инженером
(не подписан заказчиком)». Отпечаток содержания (`fingerprint.py`, общий с реестром ТК) ловит
правку после проверки: `check_signature().valid` становится `false`.

DOCX АТН: шапка (объект, договор, номер, заказчик, подрядчик), таблица позиций с колонкой
«Основание», итог, отдельные списки «не включено — требуется основание» и «не включено — нет
цены», три места для подписей (составил, проверил, согласовано заказчиком).

## 5. Что появилось в интерфейсах

**CLI:**

```bash
pto_agent cumulative --acts data/demo/acts/acts.json --estimate data/demo/smeta_v1.xlsx \
    --out out/cumulative [--strict]

pto_agent atn --out out/atn draft --items items.json \
    --acts data/demo/acts/acts.json --estimate data/demo/smeta_v1.xlsx \
    --number "АТН-1" --object-name "…" --contract "…" --customer "…" --contractor "…" \
    --reason "основание выпуска"

pto_agent atn --out out/atn confirm --atn out/atn/atn_АТН-1.json \
    --by "Иванов И.И." --role "инженер ПТО"
```

**MCP (24 → 26 инструментов):** `cumulative_ledger` и `atn_draft` (у второго
`action: draft|confirm`). В проектной схеме `prompts/tools_schema.json` у обоих прописаны
guardrails: сумма акта и сумма позиций показываются обе; `nan` не ноль; ведомость не
подтверждает выполнение; позиция без основания в акт не входит; нет цены — нет суммы; повтор не
считается дважды; подтверждение только с ФИО и ролью.

## 6. Чего этот круг не делает

* **не подтверждает выполнение работ.** Ведомость показывает предъявленное, АТН — заявленное
  с основанием; факт подтверждает человек (журнал работ, чек-листы, подписи — это круги 7 и 9);
* **не проверяет само основание.** Модуль требует вид и ссылку (лист РД, схема, письмо), но не
  сверяет, есть ли такой лист в комплекте РД и не аннулирован ли он: реестра выдачи РД
  (круг 12) пока нет;
* **не считает нормативную трудоёмкость и не заменяет смету.** Цена берётся из позиции или из
  сметы по коду, коэффициенты и индексы не применяются;
* **не подписывает и не согласовывает.** Статус после проверки инженером — «не подписан
  заказчиком».
